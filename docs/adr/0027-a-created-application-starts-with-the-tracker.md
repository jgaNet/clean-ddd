# 27. A created application starts with the Tracker and a composition root that serves it

## Context

ADR 10 made `create` give a new application the architecture and none of the business: no context, no composition root, no route. Phase 1 of the multi-agent flow ([RFC 0001](../rfc/0001-architecture-aware-multi-agent-flow.md), [the record](../evaluations/2026-10-29-flow-phase-1.md)) put three agents, one at a time, on a real project made that way, with a feature request in product words — write a note, list the notes — and read what each had to guess. Two guesses came back three times out of three, and both traced to what `create` leaves out:

- **No composition root.** Each agent wrote its own Fastify server, entry point and start command: three different shapes, none of them the reference's, because the reference's `createApplication.ts` knows four contexts and could not be copied.
- **A command answers `202 { operationId }`, and nothing in the project could answer what became of it.** Following an operation is the Tracker, and the Tracker was the reference's business as far as `create` was concerned. So all three agents ran the handler synchronously, built the operation record by hand from the in-memory bus, and answered `202 { operationId, id }` — the same workaround three times, outside the architecture, which no agent was allowed to change.

A third guess was the same gap seen from the other side: the request said *anyone* may write a note, the checklist said `requireSignedIn` first, and in the reference only a signed-in caller could read an operation — so an anonymous command could be sent and never followed.

## Decision

**A created application starts with the Tracker, the transport, and the composition root that serves them; it still starts with none of the business.**

- **The Tracker is not the business.** The domain map already says so: its subdomain, *operations*, is `generic` — recording each operation and letting a client follow it is plumbing any asynchronous application needs and none competes on. ADR 10 refused to copy someone else's domain; the Tracker has none. `create` copies it as it copies the building blocks, with the contract it publishes (`OperationComplete`), describes it in the new application's context map exactly as the reference does, and lists it in the binding's `contexts`. Where a language's own tool commits an inventory, the Tracker's lines of the reference's inventory come with it, so the new application's check starts green.
- **The transport is split from the composition.** The reference's composition root was one file that knew every context and was also the HTTP server. It is now two: a transport that names no context (`FastifyApplication.ts` in TypeScript: the per-request identity and `ExecutionContext`, CORS, the error handler, routes under one prefix, listening; without an authentication, every caller is anonymous), and the reference's composition on it (Security's authentication, the login cookie, the documentation, the notification channel, the seed). The entry point reads no settings of the reference.
- **The composition a project starts from lives in the reference, and is tested there.** `src/Bootstrap/Starter/createApplication.ts` in TypeScript wires the Tracker alone; its end-to-end suite boots it on a free port and speaks HTTP. `create` copies it *under another name* — in place of the reference's `createApplication.ts` — which is the one thing the binding's `create.copy` learned: an entry may be `{ from, to }`. That is still a copy and a rename (ADR 10): the file exists in the reference, its suite runs on every build, and a fix to it is a fix to what the next project gets.
- **An operation nobody started is followed by whoever holds its id.** `GetOperation` showed an operation to the account that started it and to an administrator, and refused everyone else; an anonymous command (a sign-up, or anything a feature lets anyone send) left an operation nobody could read. Now an operation recorded without a caller is shown to whoever asks for it by id: the id is a random UUID, given only to the caller who sent the command, in the 202, and the record carries no payload (it never did: a command may carry a secret). An operation an account started is still that account's and an administrator's; an anonymous caller asking for it is told to sign in, and another account is told it does not exist. The shared scenario asserts both, so every language answers the same.
- **The guide answers the rest in the checklists.** The command checklist now says what an anonymous command looks like (no `requireSignedIn`), that a create's new id is the operation's `result` and never part of the 202, that the barrel lines go through the alias, and where an end-to-end case goes; the context checklist names the composition root and the API prefix a context's routes are served under.

## Consequences

- A new application is a server on its first run: `yarn start:dev` (or the language's equivalent) serves `GET /v1/tracker/operations/:id`, and its end-to-end suite is not empty. The first feature adds a module and its routes to a file that exists, in the shape of the line already there.
- `create` gains a second kind of copy entry, and the loader, the build of the package and the binding's own check read both. A renamed entry is written back into the created binding under its new name, so the application's contract never names a file it does not have.
- The created project now depends on the transport's libraries (`fastify`, `@fastify/cors` in TypeScript) and has a start script. It does not get the reference's authentication: who may sign in is a context of the application's own, and until it has one every caller is anonymous — which the Tracker now answers.
- Every language carries the same split — a transport with no context, the reference's composition on it, a starting composition with its suite, the anonymous-operation rule, and a `create.copy` that ships the Tracker — each in its own idiom. TypeScript, Python and Go copy the starting composition in place of the reference's, so the copied entry point builds against it. Rust cannot: an entry point names its composition by crate name, and a workspace cannot hold two crates named `bootstrap`; so the starting composition is a crate of its own (`bootstrap-starter`) with its own three-line `main.rs`, copied as it is, and a created Rust project runs `cargo run -p bootstrap-starter`.
- A language's conventions tool travels with its tree, and its own tests had asserted on the reference's tree: in a created project they failed. Go now copies the tool without its tests; Rust's probes, compiled into the tool, run in the reference and stand down only where the binding's root is the application itself.

## When to revisit

If a second context turned out to be plumbing every application needs (an outbox relay as a context of its own, say), the same test applies: its subdomain is `generic`, it has no domain of its own, and the reference keeps a composition that boots it alone. If an application ever needed the Tracker *not* to be there — a synchronous API with no 202 — the composition root is its own to change, and the context is one entry in its binding to remove.
