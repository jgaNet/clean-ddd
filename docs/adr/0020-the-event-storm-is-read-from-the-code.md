# 20. The event storm is read from the code, and the documents show it

## Context

ADR 19 made the strategic design data: the subdomains, the context map and each context's language are declared once in `conventions/domain.yaml`, and the contracts a relationship carries are read from the code rather than written down. What the map does not show is what happens *inside* a context: who may ask for what, which command reaches which aggregate, which fact that records, who reacts to it and what they do next. That is what an event-storming session puts on a wall — orange events, blue commands, yellow actors and aggregates, purple policies, green read models, pink external systems — and the first thing a newcomer asks for when they want the whole application on one page.

A storm is usually drawn before the code exists, by hand, and kept as a photograph. Here the code exists, in four languages, and is held to canonical shapes by the checks: a wiring file that lists its commands, queries and subscriptions as data (ARCH-MODULES-DATA); an aggregate whose behaviours `record()` their events (DOMAIN-RECORDS-EVENTS); a handler that guards, loads, asks a behaviour and publishes; a controller that builds the command a route carries. Every sticky of the wall is already in the code, under a shape a tool can read.

## Decision

**The event storm is derived from the code, never drawn by hand.** The TypeScript tooling reads its tree and produces the board; the documents show it; the check keeps them current.

- **What is read.** For each context: the commands and queries its wiring lists; the aggregates (`extends AggregateRoot`) and, per behaviour, the events it records; the domain events of the context; the policies (the handlers its wiring subscribes to domain events and integration events, plus a publisher that is not a subscribed handler, which reacts to every operation — the Tracker's decorated bus); the read models a query handler answers; the ports under `Ports/` that are neither a repository nor a queries port, which are the external systems, named for the context that answers them when the map's links say so. A command or a policy is followed into the aggregate directly, or through a service (a domain service, an application service) whose methods reach a behaviour. The actor is read from the guard: `requireSignedIn()` is a signed-in account, a `guard()` that admits the administrator role alone is an administrator, nothing is anyone. The route is read from the controller method a route binds and the command that method builds, mounted where the composition root mounts it.
- **The names are the public names** the API and the Tracker already use (API-ONE-SURFACE): `ShareNote`, `NoteShared`, `GetMyNotes`. The pivots between contexts are the integration events, the same ones the context map's links carry; the storm and the map cannot disagree because they read the same thing.
- **Three renderings, one reading.** A Markdown document with Mermaid diagrams (`docs/event-storm.md`: the big picture, a lane per context with its events and a hexagon per pivot, then each context at process level with its tables); an SVG board (`docs/event-storm.svg`: a lane per context, a row per flow, stickies in the colours of the wall); and `yarn architecture storm` for the terminal, `--markdown`, `--svg` and `--json` for a tool, `storm <context>` for one lane. `yarn conventions:write` regenerates the two documents, and `yarn check:conventions` fails when they differ from what the code renders, like every other rendered block.
- **The reading recognises the canonical shapes and nothing else.** A handler that reaches an aggregate some other way, a wiring file that is not data, an event built outside `record()` do not appear on the board. That is the intended consequence: the board is a second test of the shapes the guides teach, and a sticky missing from it is a shape to fix in the code, not a regex to widen in the tool.

## Consequences

- The whole application is on one page, true to the code the day it is rendered and every day after; a feature changes the board the day it is merged, with no document to update by hand. A reviewer can read a pull request's effect on the storm from the regenerated `docs/event-storm.md` in the diff.
- The storm is the TypeScript tree's, as the map's links are. The other languages render the same application (API-ONE-SURFACE), so the board is the application's; the day every language's tool reports its own inventory, the check will hold the four equal, which is the next record.
- The specs of the reading pin what it must find on this repository's tree, so a refactor that quietly changes a canonical shape breaks a spec before it breaks the board.
- Two outcomes of one behaviour (a notification sent or failed) appear as two events from the same aggregate, not a sequence; the board does not know which conditions pick one, and does not pretend to. A read model's actor is the guard's answer, which may be broader than the data it shows (an account reads its own inbox, an administrator anyone's): the board says who may ask, the handler says what they get.
- A new kind of sticky (a hot spot, an external event) has no place yet; it is added to the reading when the code has a shape for it, never to the document by hand.

## When to revisit

If a canonical shape changes (a handler template, the wiring's data structure), the reading changes with it in the same pull request, or the board goes blank where the shape moved — which is the check's job. If a second language's inventory disagrees with TypeScript's once both exist, the application is not one application, and the scenario or the map says which server is wrong. If the board stops fitting on one page, the subdomains are the lines to cut it along.
