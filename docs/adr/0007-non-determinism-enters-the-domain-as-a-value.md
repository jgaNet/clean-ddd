# 7. Non-determinism enters the domain as a value

## Context

Some of what a use case needs is not a function of the business state: the current time, a fresh identity, a random draw, the verdict of an external model or of a person, the answer of another system. If an aggregate calls such a source itself, the same state and the same command can produce two different outcomes, a test cannot pin the behaviour, and a replay would ask the source again. With coding agents and language models entering applications, the question stops being academic: where does a probabilistic answer meet the deterministic rules?

## Decision

The domain stays deterministic by taking every such input **as a value**:

- **Time** is a parameter with a default: `authenticate(now: Date = new Date())`, `recordAttempt(channel, succeeded, at = new Date())`. Production passes nothing; a test passes the instant it wants.
- **Identity** is generated by the domain (`Id.generate()`, [ADR 2](0002-identity-is-generated-by-the-domain.md)): an id carries no business meaning and is never compared for anything but equality, so its randomness cannot change an outcome.
- **Anything else** — a random draw, an external model, a person, another system — lives behind a **port** named for what it decides, not for the technology (`IPasswordHasher`, not `IBcrypt`; an `INoteTagSuggestions`, not an `ILlmService`). Its result is a **plain value** that the aggregate validates like any other input and **may refuse**: the source proposes, the domain disposes.
- When a replay must not ask the source again (an audit, a rebuild from events, a model that has since changed), the value is **persisted with its provenance** — which source, which version, when — and the aggregate is fed the persisted value.

## Consequences

- Domain and handler specs never touch a clock, a random generator or a model: they pass values. The one adapter that talks to the non-deterministic source is tested on its own, or replaced by a stub.
- The verdict of a model is data, so the rules that decide what a verdict may do stay in the aggregate; a model can never become the authority on an invariant.
- The repository has no example of a persisted, provenance-carrying decision yet. If one is added, it is a port in the Application layer of the context that needs it, a value type next to it, and an adapter in its infrastructure; not a new kind of message.

## When to revisit

If a context comes to depend on a model for most of its decisions, the persisted decision may deserve to become an aggregate of its own, with its own lifecycle (proposed, accepted, overridden). Until then it is a value.
