# Flow, phase 3 — a run killed mid-way and resumed, the same run on a second runner, the slice's pack

**Date:** 2026-10-30 · **Proposal:** [RFC 0001](../rfc/0001-architecture-aware-multi-agent-flow.md), phase 3 · **Driver:** [`.claude/flow/run-slices.mjs`](../../.claude/flow/run-slices.mjs), [`runners.mjs`](../../.claude/flow/runners.mjs) · **The pack:** [`tools/src/pack.ts`](../../tools/src/pack.ts) · **The plan:** [`flow/phase3/execution-plan.yaml`](flow/phase3/execution-plan.yaml) · **Logs:** `flow/phase3-*.jsonl`

## The exit criterion

> A run killed mid-way resumes to the same result; the same run passes on two runners.

**Met.** The feature is phase 2's: *notify recipients when a shared note is archived*. The project, the contract stage and the frozen contract are the ones phase 2 left; only the project's tooling moved, to the package that has `pack` (base `9c4da43`).

- **Killed and resumed, on Claude Code headless (`claude-cli`), run `p3-cli-2`.** Both agents had been working for about two minutes when the driver was killed with `SIGKILL`. Both were still running, orphaned. `--resume` read the log and found the two leases. It stopped each agent by its process group and continued each conversation, telling the agent it had been interrupted. Both slices passed their gates, and the integration passed: the gate, the storm entirely carried, and the acceptance test 3 of 3. This is the result an uninterrupted run reaches, as the next run shows.
- **Whole, on the Claude Agent SDK (`claude-sdk`), run `p3-sdk`.** The same execution plan with the other runner: COMPLETED, with the same three checks.

I re-ran the gate, the storm check and the acceptance test on both integrated branches myself, and they agreed with the driver. Outside `src/Contexts`, each branch differs from the base only by the three contract files the single writer marks carried. Nobody edited the contract or the code after the contract stage.

**Cancel.** `--cancel` reads the driver's pid from the run's lock file and signals the driver. The driver stopped both agents by their process groups, which were gone a second later. It logged each slice and the run `CANCELLED`, and removed its leases and its lock. A `--resume` of a cancelled run is refused: CANCELLED is final.

## What the runs found

### In the driver — fixed on this branch

- **A gate that passes on half a slice let it through.** In `p3-cli`, the first resume checked each lost slice as it stood and continued it only if the check failed. The Notes agent had been killed with seven files written and not committed; the driver committed them, and the gate passed on them. The Notifications agent had not written anything yet, and the gate passed on the unchanged base. Both slices were PASSED, one half done and one not started. The gate says that a slice's code holds to the architecture and to its own tests. It cannot say that the slice did what its plan asked, and only the agent knows what was left. The fix: a slice whose agent was running when its driver died is always continued, told it was interrupted. Only a slice whose agent had finished, and that the driver was checking, is checked again. A resume that is itself interrupted resumes from the state before it. In `p3-cli-2`, the Notes agent had committed its work before the kill; told it was interrupted, it re-ran the gate and reported in three turns. The Notifications agent had eight files uncommitted and took twelve turns to finish them.
- **An empty slice blocked the integration.** The Notifications slice of `p3-cli` reached the writer with nothing in it, and `git apply` refuses an empty patch. An empty slice diff is now logged and skipped. Since a lost slice is now always continued, this should no longer happen, but an empty diff is not a conflict.
- **A continued conversation's cost.** Phase 2 added up the figures a continued conversation reported; the driver now keeps a slice's latest figure ([phase 2's record](2026-10-29-flow-phase-2.md) is corrected).

### In what the runner can tell — open

- **The spend of a killed agent is not reported anywhere.** An agent stopped with `SIGKILL` prints no result, and its continuation reports what it saw itself: three turns and $0.09 for the Notes slice, which had already done its work before the kill. So `p3-cli-2`'s $0.69 is a lower bound. The two killed sessions ran about two minutes each; at `p3-sdk`'s rate that is roughly another $1.20, an estimate rather than a measurement. The RFC asks that the source of every usage number be confirmed or recorded as absent (phase 1). For a killed agent, it is absent. Reading it from the provider's usage records, rather than from the agent, would close it.
- **The SDK's agent is not in a process group of its own.** A driver killed with `SIGKILL` while a `claude-sdk` slice runs may leave the agent running, and the lease has no group to stop it by. Cancel stops it through the SDK's abort signal; a crash does not. This was not exercised. The driver's README says so, and the kill-and-resume run used the CLI runner, which can be stopped by group.

### In the pack — one fixed, one open

Every agent of `p3-cli-2` and `p3-sdk` ran `yarn architecture pack` first, as its brief asked, and read the reference files it pointed to. That took them in a few turns to what phase 2's agents had to find:

- the reference's reaction that publishes a fact for other contexts;
- its anti-corruption handler;
- its Notification aggregate.

None wrote outside its own context. The plans still say in words which half is whose, as phase 2 needed; the pack draws that line itself, so a next contract stage need not.

- **The examples were newer than the project's building blocks — fixed: the pack says so.** The project was created before [ADR 30](../adr/0030-a-reaction-is-a-transaction-of-its-own.md). Its building blocks are the copy `create` made, and they have no `publishIntegrationEvent` and no transaction of a reaction's own. The package that shows the examples is newer, and its reference reactions use both.

  The two Notes agents of these runs went different ways. The `p3-cli-2` one published straight to the bus, as phase 2's agents did. The `p3-sdk` one read the reference's `DomainEvents.ts` and wrote a private copy of `publishIntegrationEvent` into its own handler. To get past a transaction it could not see, it put an `await Promise.resolve()` before it, and it said in a comment that the building blocks lacked the function.

  Neither is wrong for the gate. Both are a slice working around what the project lacks. That gap is an architecture task: bringing the building blocks up to the reference. The pack now compares the project's building blocks with those of the reference its examples come from, and lists the files that differ. For this project, it lists the seven files ADR 30 changed. It also tells the agent to read an example for its shape, to call only what the project has, and to report what the project lacks rather than write it.
- **Bringing a created project's building blocks up to date — open.** `create` copies the building blocks once; nothing upgrades them. The project of these runs still lacks ADR 30, so its reactions carry the questions ADR 30 closed. One example is the Notifications consumer's `withTransaction()`, which is nested inside the publisher's relay. Upgrading means re-copying the tree `create` copied, as an architecture task in the project, with its own ADR. A command that shows that difference and applies it is the next piece of tooling this asks for.

## Next

Phase 3's criterion is met. Phase 4 of the RFC is the benchmark: arms A, B, C and C′ on the backlog, three runs each. Two findings above bear on it:

- **The pack is now one of the things an agent is given.** Whether it helps is the benchmark's question, not an assumption: an arm with the pack and an arm without it.
- **The cost of a run interrupted and resumed is not fully measurable from the agents.** A benchmark that kills runs needs the provider's records, or must not count those runs' cost.
