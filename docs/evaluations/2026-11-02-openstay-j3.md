# OpenStay's J3: fifteen more features on the pilot's trees, and a change not announced in advance

**Date:** 2026-11-01 to 2026-11-02 · **Protocol:** [`benchmark/openstay/`](benchmark/openstay/README.md) · **The kit, written and rehearsed before the runs:** [`benchmark/openstay/j3/`](benchmark/openstay/j3/README.md) · **Logs, plans, grades, metrics, trees, the reading:** [`flow/openstay-j3/`](flow/openstay-j3/README.md) · **The pilot (J2):** [its record](2026-11-01-openstay-pilot.md)

J3 took the six trees of the pilot, each from its pilot head, through requests 11 to 25:
- amenities and house rules, search filters, favourites, a map;
- seasonal prices, discounts, a booking window, arrival days;
- changing a booking's dates, holds, a host's dashboard, changing several calendars at once;
- organisations, collaborators and permissions, and the conditions as accepted.

Request 24 (collaborators) is the change not announced in advance: it changes who may act on a listing across most earlier features, and nothing in requests 11 to 23 announced it.

As in the pilot, each feature started with the smallest model and went one step up only when its attempt failed. The steps were Claude Haiku 5.5, then Sonnet 5.5, then Opus 5.5. After every attempt, the tree was graded on the hidden tests of every feature so far, 1 to n, so that a regression counts. There were no strongest-model witnesses this time (the maintainer's decision).

## The hypothesis, after twenty-five features

The protocol's hypothesis, written before any run: *the step features need rises faster in the simple arm than in the Clean DDD arm as the trees grow.*

| Delivered above the smallest model (real escalations) | Simple | Clean DDD |
| --- | --- | --- |
| Features 1–10 (the pilot) | 0 of 30 | 1 of 30 |
| Features 11–25 (J3) | 0 of 45 | 1 of 45 |
| Delivered only by the strongest | 0 of 75 | 0 of 75 |

**Not supported at twenty-five features.** The trees are now 5,000 (simple) to 15,000 (Clean DDD) source lines. Neither arm needed a stronger model where it really failed, apart from one feature each in the Clean DDD arm. That held for the change not announced in advance too: request 24 was delivered at the smallest step in all six trees.

What did move is cost and time:
- **The cost gap halved.** In the pilot the simple arm was 3.5 to 7.7 times cheaper; in J3, 1.5 to 3.6 times.
- **Agent time reversed** in the Clean DDD arm's favour.

Both are the direction the hypothesis expects, on a measure the hypothesis did not name. Two windows of a series are not a trend.

## Robustness

- **Both gradings pass everywhere.** That includes the chaos test of request 10, with J3's aimed kills: five rounds kill the server as soon as a booking is answered.
- **The independent reading found no crash or second-process window in any tree** (O7, all pass). Every Clean DDD tree had one in the pilot; the relay fix ported before J3 closed them.
- **Before the runs, the aimed kills found two defects in clean-2.** First, the pilot's relay lost notices: 5 of them under the new kills. Then, with the relay fixed, the tree owed two notices for one booking, because neither its inbox nor its table refused a second. The maintainer chose to fix the second before the runs (commit `141b51f`, the tree's ADR 14), so that the tree would not stop at feature 11 on a defect older than J3. This is tree code written by the experimenter, named in the biases.
- **Porting the relay fix into the trees found a defect in the reference.** In TypeScript, Python and Rust, the relay kept its guard against handing out an entry still on its way per outbox object. A durable outbox built for each unit of work defeats it, and two of the three Clean DDD trees build one. The reference now keeps the guard by entry id, with a test in each language (`d3db3b1`); Go already did.
- **The chaos test failed once in the ladder:** simple-2, feature 25. It did not fail when replayed three times, nor in the second grading. Feature 25 opened no window there: it writes the conditions in the booking's own transaction, beside the notice.

## Maintainability: the independent reading

A fresh agent that did not run J3 read the six final trees against [the rubric](benchmark/openstay/j3/reading.md), written while J3 ran and before any final tree was read ([its report](flow/openstay-j3/reading.md)). Three of its claims were checked against the code before use, and all three hold:
- clean-2 tests `=== 'manager'` in about twenty handlers;
- clean-1 serves the bulk routes to managers;
- every simple tree takes the write lock before taking nights.

**The architecture bought the same structure as in the pilot:**
- contexts apart, through ports;
- time passed as a parameter;
- refusals returned as values.

Every simple tree has an import cycle between listings and bookings, reads other parts' tables, and reads the clock inline somewhere.

**It did not buy rules stated once (O1).** No tree states every rule once, in either arm; the Clean DDD trees repeat fewer (4–6 against 5–7).
- **Every tree** restates the stay limits in its search.
- **The simple trees** restate the booking window and the arrival days in SQL.
- **The Clean DDD trees** decide whether a hold still holds in three places: the aggregate, a copy on the calendar, and SQL.

**Two of three Clean DDD trees opened a permission hole.** clean-1 and clean-3 let an organisation's manager use the host-only bulk routes (`/hosts/me/block`, `/hosts/me/seasonal-prices`), against request 24 and, in clean-1, against the tree's own ADR. No test covers it. All three simple trees and clean-2 kept those routes host-only. This is the kit's gap as much as the trees': the review asked request 24 to say so (R12), and no test was added for it.

**The change not announced in advance landed in one place in five trees of six** (O10). It cost more files in the Clean DDD arm:
- 9 to 13 files in the simple trees;
- 71 to 87 in the Clean DDD trees, where 27 to 30 earlier handlers were each given the permission port;
- clean-2 decided the permission in one port, but copied the meaning of "manager" into 19 handlers.

**The change probes still favour the simple arm on files, less so on reading:**

| Probe | Simple: files (lines read) | Clean DDD: files (lines read) |
| --- | --- | --- |
| An accountant: a member who reads lines and refunds only | 3–6 (1,000–1,300) | 10–11 (800–900) |
| A cleaning day between stays | 1–2 (300–400) | 2 (350–400) |
| Holds that cost a deposit | 4–7 (700–800) | 15–18 (900–1,000) |

The Clean DDD trees need fewer lines read to find the accountant's files, but more files to change. Part of that is the architecture's one file per thing, and the port, event and handler each cross-context change needs.

## What follows

- **The kit should test what O8 found.** A manager using the host's own `/hosts/me` routes is refused (request 24, R12). This is an amendment for any later run, applied to every tree alike.
- **The harness should grade on a quieter machine.** Five of six escalations were load. The protocol's escalation rule cannot tell load from a defect at the moment it happens. A grader that runs the failing feature again, alone, before escalating would save the money and the noise.
- **J4** is fifty features: payments, a storage migration, a domain split. The protocol's decision (continue, adjust or stop) is the maintainer's.
  - **The question is still open.** Neither arm needed stronger models as it grew, the cost gap is narrowing, and agent time has crossed.
  - **Neither stop condition holds.**

## Biases

- **Author of everything,** as in every campaign: the architecture, the requests, the tests, the storms' proposals, the rubric, and this record.
- **The experimenter wrote tree code.** These commits are recorded in each tree with an ADR:
  - the relay fix in the three Clean DDD trees (the reference's);
  - clean-2's one-notice rule, the maintainer's decision.

  The simple trees got none, and needed none.
- **Machine load.** Four trees at once on four processors. simple-3 and clean-3 started later, with fewer neighbours, so their lead times are not comparable with the others'. My replays added load.
- **One reader,** an agent, who could not be blind to the arm. Three of its claims were checked.
- **The storms are not priced in time.** The maintainer accepted the session's proposals in one answer.
- **Small series.** Three trees per arm, two windows.
