# Flow, phase 1 — one feature, one isolated agent, the gate's verdict against a person's reading

**Date:** 2026-10-29 · **Proposal:** [RFC 0001](../rfc/0001-architecture-aware-multi-agent-flow.md), phase 1 · **Logs:** [`flow/phase1-notes-1.jsonl`](flow/phase1-notes-1.jsonl), [`-2`](flow/phase1-notes-2.jsonl), [`-3`](flow/phase1-notes-3.jsonl)

## What was run

- **The project.** A real application, not this reference: `clean-ddd create notes-app --language typescript` from the package built on this branch, installed from its tarball (the package is not on npm yet), committed as its own repository.
- **The architecture task, done first and by hand.** Declaring the first context took four things, not two: `Notes` in the binding's `contexts`, its subdomain and description in the context map, its directory with a wiring file (an empty `Module`; ARCH-CONTEXT-DECLARED refuses a declared context without one), and the documents re-rendered (`yarn conventions:write`). That commit is the base every run started from; the gate passes on it.
- **The request**, in product words, the same for the three runs:

  > People want to keep notes. Anyone can write a note: a title and a text. The title is required and at most 100 characters; the text may be empty. Anyone can read the list of notes, the most recent first. Over the HTTP API: writing a note answers with the new note's id; the list answers, for each note, its id, its title, its text and when it was written.

- **The runs.** Three, at the same time, each by [`.claude/flow/run-feature.mjs`](../../.claude/flow/run-feature.mjs): its own git worktree and branch from the base, Claude Code headless (`claude -p`, Opus 5.5) given the request and the project's own `feature-author` brief, then the gate run by the driver — never read from the agent's report — and every step in a JSONL log.

## The exit criterion

> On three runs the gate's verdict matches a person's reading of the same checks; the source of every usage number is confirmed or recorded as absent.

**Met.**

| Run | Gate (driver) | The same checks, re-run by hand | Unit tests added | End-to-end tests | Over HTTP |
| --- | --- | --- | --- | --- | --- |
| 1 | PASS | mode, conventions, format, lint, types: all pass | 15 | 5, real ones | writes, refuses a 101-character title (400), lists newest first |
| 2 | PASS | all pass | 16 | 3 | the same, under `/v1/notes` |
| 3 | PASS | all pass | 20 | 5 | the same, under `/v1/notes` |

"By hand" means each command run on its own in the worktree, outside the gate, then the tests counted against the base's (57 unit tests, no end-to-end test — so the end-to-end script's `--passWithNoTests` could not have hidden an empty suite: each run wrote one), and each server started on its own port and called with `curl`. No disagreement between the gate and the reading.

**Usage source: confirmed.** `claude -p --output-format json` reports the total cost and, per model, input, output, cache-read and cache-creation tokens; the driver logs those fields and nothing else.

| Run | Turns | Agent time | Output tokens | Cache read | Cache creation | Cost | Gate time |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 37 | 5 min 37 s | 29,220 | 3.40 M | 114 k | $2.18 | ~15 s |
| 2 | 31 | 5 min 18 s | 26,792 | 2.97 M | 105 k | $1.97 | ~15 s |

A tiny model call the runner makes on its own (about 1,450 input tokens) is in every log and in the cost. Three runs of one feature are a measurement of this setup, not a benchmark: no comparison is drawn from them.

## What the runs found

### In the driver — fixed on this branch

- **Worktrees inside the project were walked by the project's own tools.** With the three worktrees under `notes-app/.flow/`, the project's `yarn test:units` ran 279 tests instead of 57 — its own and the three runs'. Worktrees now go beside the project (`<project>.flow/`).
- **A shared `node_modules`.** Each worktree's `node_modules` was a link to the project's, so the three agents' `yarn add fastify` (and one's `yarn add tsx`) wrote into one install, concurrently. Each worktree now gets its own hard-linked copy. Both fixes were checked by a no-change smoke run.

### In what a created project gives an agent — fixed on this branch, found while preparing the runs

- **A created project failed its own check as soon as its first context was declared**: its README had no block for the dependency table, and `--write` can only fill a block whose marker exists. `create` now writes the block; a spec declares a first context and stays green.
- **The project's `feature-author` agent and `feature` skill spoke of the reference's four directories** (`cd typescript`, `rust/`, …), which a created project does not have. Both now read right in either, and end with the gate.

### In what a created project gives an agent — open, the next work

The three reports were written independently and agree. Each line is a guess an agent had to make, and so a sentence or an example missing for a real project:

| Guess | Runs | What it asks for |
| --- | --- | --- |
| **No composition root and nothing to copy for one.** Each run wrote its own Fastify server, entry point and start command; three different shapes. | 3 / 3 | A composition root a created project can start from, or a checklist for it that names the reference's |
| **"Answers with the new note's id" against a command's `202 { operationId }`.** All three ran the handler synchronously through `Module.getCommand()` and built the operation record by hand, copying code from the in-memory bus, and answered `202 { operationId, id }`. | 3 / 3 | A decision: how a create answers with its id — a building block that runs a command and returns its operation, or the guide saying to poll the operation. An architecture question, which no agent was allowed to answer |
| **"Anyone" against the checklist's `requireSignedIn` first.** | 3 / 3 | The checklist saying what an anonymous command looks like |
| **Where the end-to-end spec goes**, since a context holds only its layers and its wiring. Two put it in `Presentation/`, one in `Bootstrap/`. | 3 / 3 | One sentence in the guide |
| **The route prefix.** Two chose `/v1` from a comment; one used none. | 2 / 3 | The prefix said once, or left to the request |
| **The concepts with no example in a created project** (aggregate, handlers, controller, routes, repository): the agents read the building blocks, the reference's comments, and in one case the inventory parser's regular expressions. | 2 / 3 named it | RFC gap G7: `pack` drawing the examples from the bundled reference |
| **The command barrel.** The checklist says "two lines in `Commands/index.ts`"; the agents wrote them relative, the linter refused, they switched to the alias. | 2 / 3 | The checklist line saying "through the alias" |

The first two would have been decided by the contract stage the RFC proposes for later phases; in phase 1 the agents decided them alone, three times, and three times alike for the second and differently for the first.

### In the environment

The container runs Node 22 and the created project asks for 24: yarn refuses to run its scripts unless told to ignore engines (`YARN_IGNORE_ENGINES=true`, set by the driver), and Jest cannot load the dependency of Fastify's in-process test client, so the three runs tested over a real port. Neither is the project's or the tooling's.

### Closed since, before phase 2

[ADR 27](../adr/0027-a-created-application-starts-with-the-tracker.md) takes the decision the second guess asked for, and the rest follow from it or are a sentence in a checklist:

| Guess | Now |
| --- | --- |
| No composition root | A created project starts with one: the transport, which knows no context, and the composition that serves the Tracker, a file of the reference tested there and copied in place of the reference's own, with its end-to-end suite. A new context is one module and one routes line in it. |
| "Answers with the new note's id" | The Tracker ships with every created project; the command checklist says a create's id is the operation's `result`, read at `GET /v1/tracker/operations/:id`, and never part of the 202. |
| "Anyone" against `requireSignedIn` | The command checklist says an anonymous command has no `requireSignedIn`; an operation nobody started is now shown to whoever holds its id, in every language the scenario holds. |
| Where the end-to-end spec goes | The command checklist names the place (beside the routes) and the suite to copy (the composition root's own). |
| The route prefix | The transport serves every route under the API prefix (`v1` unless `API_PREFIX` says otherwise); the context checklist says so. |
| The command barrel | The checklist line says "through the alias". |
| No feature-level example | Still open: RFC gap G7 (`pack`). The Tracker gives a created project a query handler, a controller, routes and a wiring file to read, but no aggregate nor command. |
