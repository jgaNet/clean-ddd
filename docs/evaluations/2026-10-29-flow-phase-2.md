# Flow, phase 2 — one cross-context feature, two slices in parallel, one writer that integrates

**Date:** 2026-10-29 · **Proposal:** [RFC 0001](../rfc/0001-architecture-aware-multi-agent-flow.md), phase 2 · **Driver:** [`.claude/flow/run-slices.mjs`](../../.claude/flow/run-slices.mjs) · **The contract:** [`flow/phase2/`](flow/phase2) · **Logs:** `flow/phase2-*.jsonl`

## The exit criterion

> Feature 5 of the backlog delivered twice into a green pull request with no human edit after the contract stage.

**Met**, on runs 4 and 5. The feature is *notify recipients when a shared note is archived*. In each run, two agents wrote it at the same time, one in `Notes`, one in `Notifications`, each in its own worktree and blind to the other. Each passed the gate the driver ran on its slice. The single writer applied both patches and passed, on the combination:

- the gate: mode, conventions, format, lint, types, unit and end-to-end tests;
- the storm, entirely carried;
- the acceptance test written in the contract stage, 3 of 3.

Neither run needed a retry. Nobody edited the contract or the code after the contract stage. I re-ran every one of those checks on both integrated branches myself, and they agreed with the driver.

What "pull request" means here: the project `clean-ddd create` made has no remote, so the deliverable is the integrated branch, `run/notify-<n>/integration-1`, ready to push.

Runs 1 to 3 did not get there, and each failure was the contract's tooling, not the agents. Two architecture changes were needed before a two-slice run could pass at all: [ADR 28](../adr/0028-a-relationship-is-decided-before-its-code.md) and [ADR 29](../adr/0029-a-contract-may-be-in-progress.md). The person upgraded the project's tooling between runs, as an architecture change. The contract itself — the storm, the plans, the integration event and the acceptance test — is byte for byte the one written in the contract stage.

## What was run

**The project.** `clean-ddd create notes-app`, from this branch's package, after [ADR 27](../adr/0027-a-created-application-starts-with-the-tracker.md), so it starts with the Tracker. Its base was grown the way the RFC's backlog grows a real product: one feature at a time, each written by an isolated agent through the phase-1 driver, in product words. Each feature came after its architecture task, which a person did: declare the context or the relationship, write the project's own ADR, re-render.

The Accounts run cost twice its price. The disk filled during the run, from other work in the container. The agent had written everything, could no longer see any command's output, waited 28 minutes and reported exactly that, without committing anything half-checked. Once space was freed it was continued in the same conversation; that is when the driver's resume became `--continue`.

**The contract stage of feature 5.** A person made it, and the domain's open questions went to the maintainer. All four were decided as proposed:

- who is notified: the accounts the note is shared with, never the owner;
- an archive, restore, archive: one notification per archiving;
- what a recipient can do: list their own, most recent first, nothing more;
- whether the contract is approved before the agents start: no separate approval once it passes the tooling.

It produced:

- an acceptance test of the whole flow over HTTP. It failed at the base for the right reason: the base flow worked up to `GET /v1/notifications`, which did not exist yet.

## What the runs found

### In the architecture — fixed on this branch

- **A relationship could not be declared before its code.** This was found while preparing the base, not by a run. CTX-MAP-DECLARED says a new relationship is a decision written down before it is merged, and also refused a declared relationship that nothing carried. When the person declared Accounts → Notes first, as the flow requires, the project's gate turned red; a feature agent may not write the map, so nobody could write it. [ADR 28](../adr/0028-a-relationship-is-decided-before-its-code.md) lets a relationship be declared `planned: true`. A link the map does not declare is still refused.

- **A contract had no word for *in progress*.** In run 1, both agents wrote and committed their slice with every test passing, then stopped with the same report. The conventions check refused a storm `done: false` that the code partly carried, and a plan whose `new` parts existed. Changing the flags would not have helped: the Notifications agent tried it and saw the done storm refused for the part the Notes slice owed. No single worktree could pass.

  The first version of [ADR 29](../adr/0029-a-contract-may-be-in-progress.md) allowed *partly* carried storms and plans. Runs 2 and 3 then stopped all four slices the same way: each slice writes its *whole* plan, so in its worktree the plan was fully carried and had to say `new: false`, in a frozen file. Each of the four agents checked that this one flag was all that stood between its slice and a passing gate. The fix: a plan is in progress while its feature's storm is not done. At integration, the single writer marks the storm done and the plans' parts not new, and the gate then holds the combined code to all of it.

  With that tooling, and without changing their code, the four blocked slices of runs 2 and 3 passed their gates. Replayed offline, run 1's two slices integrated green: gate, storm and acceptance.

Every blocked slice stopped rather than touch the frozen contract. The brief asked for that, and it is what the RFC's state `BLOCKED` is for. None of the eight blocked slices of runs 1 to 3 wrote outside its context.

### In the driver — fixed on this branch

- **Resuming an agent.** Run from inside a Claude Code session, every agent reported the *parent's* session id, inherited through the environment, so `--resume <id>` would have resumed the wrong conversation. A slice sent back now continues the latest conversation in its own worktree (`--continue`), and the id is no longer logged.

### In what the guide leaves an agent to decide — open, the next work

Four agents wrote the feature in runs 4 and 5. Each line below is a guess at least two of them made, or a choice on which two of them differed.

| Question | Runs | What happened | What it asks for |
| --- | --- | --- | --- |
| How a reaction publishes an integration event: through the outbox, or straight to the bus, and with which message id | 3 of 4 | All published straight to the bus with a new id; two said a redelivered domain event would then reach the consumer twice | A sentence in the guide, and possibly the building block: a reaction's publication as durable as a command's |
| Whether a reaction that saves several aggregates opens a transaction | 2 of 2 consumers | Both saved one at a time, outside any transaction | A sentence, or a base-class answer |
| Whether a consumer's fan-out must be idempotent per recipient | 2 of 2 consumers | Run 4 guarded each recipient (`existsFor`); run 5 did not, and said so | The checklist of an anti-corruption handler |
| A domain event payload: carry the facts of the moment, or let the reaction read them back; a `Date` or an ISO string | 2 of 2 producers | Both carried the recipients in the event, rightly; one used a `Date`, the other a string | One sentence for each |
| A context that only consumes cannot show its flow in its own end-to-end suite (ARCH-E2E forbids reaching the bus) | 2 of 2 consumers | Both tested the empty list and the 403 end to end, and the fan-out in the handler's spec | The guide saying so; the acceptance test is where the flow is shown |
| `EventHandler`'s header names example files a created project does not have | 1 of 4 | — | RFC gap G7 (`pack`) |

The first three are not guesses about shape: they decide whether a notification can be lost or told twice. They are the next sentences for the guide, and possibly a building block.

### In the tooling a run leans on — open

- **`plan explain` describes the whole feature.** It lists the other slice's file too (*the anti-corruption handler in Notifications* in the Notes plan), and says *Change* for an integration contract that is frozen. The plans' intent had to say so in words. A slice needs a view of its own part: RFC gap G7, the `pack` command.
- **The storm cannot say that an existing domain event is widened.** Both Notes slices enlarged `NoteArchivedEvent`, and the inventory has no word for it. That is right, since the inventory names events, not payloads; one agent asked.

## Next

Phase 2's criterion is met. Phase 3 of the RFC is resume, cancel and a second runner. Before that, the guesses above are worth closing, because they are about correctness rather than shape:

- what a reaction must do to publish durably;
- the transaction of a reaction that saves several aggregates;
- the idempotency of a consumer's fan-out.

They would take the next agent from "probably right" to "right by construction". `pack`, which the RFC schedules for phase 3, would answer the slice's view of a plan.
