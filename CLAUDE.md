# Working on this repository (guide for AI assistance)

This is a **reference implementation** of Clean Architecture + Domain-Driven Design, written in several programming languages from one architecture. The architecture is data ([`conventions/`](conventions/README.md)); each language is a directory with its own toolchain, its own guide and a binding that maps the contract onto its files. Before changing anything, read the [README](README.md): it says which languages exist and maps every concept to the file that shows it in each, and links the decisions in [`docs/adr`](docs/adr).

## Which guide to read

A change to **code** happens in one language's directory, under that language's guide: [`typescript/CLAUDE.md`](typescript/CLAUDE.md) for TypeScript, [`rust/CLAUDE.md`](rust/CLAUDE.md) for Rust, [`python/CLAUDE.md`](python/CLAUDE.md) for Python, [`go/CLAUDE.md`](go/CLAUDE.md) for Go. Its commands run from that directory (`cd typescript`; `cd rust`; `cd python`; `cd go`). The tooling at the root ([`tools/`](tools/README.md), `yarn install` once here) answers questions about the contract itself, for any language: `yarn architecture rule <ID>`, `yarn architecture concept <id>`, `yarn architecture checklist command --language rust`; from a language's directory, `yarn --cwd .. architecture …` answers for that language.

A change to the **architecture** — a rule, a layer, a decision, a binding, a new language — happens here, at the root, and is an architecture change in the sense of [ADR 9](docs/adr/0009-work-is-done-in-one-of-two-modes.md): `yarn architecture mode architecture` asks for the ADR that explains it.

## Where things are

```
conventions/architecture.yaml   the contract: layers, who may import whom, every rule under its id, the HTTP
                                grammar, the kinds of thing a feature is made of, the two modes. Names no file.
conventions/concepts.yaml       the vocabulary: every concept, its rules, its decisions. Names no file.
conventions/domain.yaml         the domain: the subdomains and their kind, each context's purpose and language, the
                                context map (every relationship between two contexts, its pattern, its mechanism, why).
                                Names no file; the contracts a relationship carries are read from the code.
conventions/<language>.yaml     a binding (typescript.yaml, rust.yaml, python.yaml, go.yaml): that language's trees and aliases, its
                                contexts, what holds each rule there, the file that shows each concept and each
                                rule, its checklists.
conventions/plans/              feature plans, each written for one language, validated on every build
conventions/storms/             expected storms: what a facilitated session decided a feature adds, in the inventory's
                                words (one file for every language), held to the code by the check
docs/adr/                       the decisions; docs/evaluations/ the fresh-agent evaluations
docs/event-storm.md             the event storm, read from the TypeScript tree and rendered with its board (never edited)
docs/inventory/<language>.json  what that language's tree says the application is, written by its tool, held equal to
                                the others by the check (never edited)
typescript/                     the TypeScript implementation (src/, the configs, its linter eslint.config.js)
rust/                           the Rust implementation (a crate per layer under src/, tools/conventions)
python/                         the Python implementation (a package per layer under src/, tools/conventions.py)
go/                             the Go implementation (a package per layer, tools/conventions)
tools/                          the tooling, one package for every language: the contract API, the CLI, the conventions check
                                (tools/src, built by tools/build.mjs, published to npm as clean-ddd); package.json at the root
                                drives it: yarn architecture, yarn check:conventions, yarn conventions:write
.claude/                        the feature skill and the feature-author agent
```

Every path the contract carries is relative to this directory, in every tool's output and in every document: `typescript/src/Contexts/Notes/Domain/Note/Note.ts`, `docs/adr/0001-….md`.

## The rules (enforced, in every language)

Each rule has a stable id; `yarn architecture rule <ID>` explains it, `--json` for a tool. The list below is rendered from [`conventions/architecture.yaml`](conventions/architecture.yaml); a language's binding says which tool holds each enforcement word there (ESLint for `linter` in TypeScript) and which file shows the rule.

- **A relative import names a sibling file and nothing else; anything across directories goes through the path the import rules are written against.** The import rules are written against those paths (an alias, a crate path); a relative path across directories would bypass them. *Fix:* Import through the path the rules match on; the binding names it. *(ARCH-RELATIVE; linter)*
- **Dependencies point inward and contexts stay apart — each file imports only what its row of the dependency table allows; there is no exception and none may be added.** A boundary that can be crossed when convenient is not a boundary; the table is the architecture. *Fix:* Fix a violation with a port, an integration event or a move, never by silencing the linter (the conventions check refuses a silenced rule). *(ARCH-INWARD; linter)*
- **The building blocks import nothing outside themselves, not even the shared kernel; the shared kernel imports the building blocks and no context.** The building blocks are mechanics and must know no vocabulary, not even the roles; the shared kernel is the part of the domain model every context agrees on, built on those mechanics. *Fix:* Vocabulary (a role, an email, a policy) goes to the shared kernel; mechanics go to the building blocks; a context's things stay in the context. *(ARCH-TREES; linter)*
- **Every directory under the contexts tree is a context declared in the language's binding, holds only the declared layers and its wiring file.** An undeclared context has no import rule applying to it. *Fix:* Add the context to `contexts` in the binding; move stray files into a layer. *(ARCH-CONTEXT-DECLARED; check)*
- **A context's wiring is one file building a Module as data — its name, its commands, its queries, its domain event and integration event handlers; anything else it exposes is a named export of that file. No container, no builder, no service locator.** Wiring that is data can be read in one screen and explained to an agent; a container hides which handler answers which command. *Fix:* Construct the handler, pass its ports, list it in the Module. *(ARCH-MODULES-DATA; review)*
- **A command has exactly one handler — the Module lists it once, with one handler, and every command a route or a policy builds is one the Module lists; a fact may have any number of subscribers.** Commands and facts share one bus, and they differ in what an answer is — a command's outcome is its handler's result, so two handlers would answer with two outcomes and none with no outcome, while a fact is told to whoever listens and nobody is a fine answer. *Fix:* List the command once in the Module with the one handler that decides it; a second reaction to the same intent is a policy on the fact that handler records, not a second handler; a command a route builds and nobody answers is a handler missing from the wiring. *(ARCH-ONE-HANDLER; check)*
- **ExecutionContext carries what exists per request and nothing else — who is calling, the trace, the transaction, the bus, the logger. A mailer, a clock, a model client is a constructor dependency of the handler that needs it.** A context that grows is a service locator with a better name; a handler's needs belong in its signature. *Fix:* Add a port, inject it in the constructor, pass it from the wiring file. *(ARCH-EXECUTION-CONTEXT; review)*
- **A refused command or query is a failed Result value, never a thrown exception; throwing (or panicking) is for programming errors and corrupted state only.** A refusal is a normal outcome the caller must handle; a throw is a crash that hides it. *Fix:* Return a failed Result carrying the rule's exception from the behaviour; let the handler pass it on; the base handler turns a stray throw into a failed operation. *(DOMAIN-RESULT; tests)*
- **Only an aggregate root records domain events (`record(...)` inside a behaviour); handlers never construct one, they call `publishDomainEvents(aggregate, context)` after saving.** The fact belongs to the object whose rule produced it; a handler that builds events can lie about what happened. *Fix:* Move the `record()` call into the behaviour that changes the state. *(DOMAIN-RECORDS-EVENTS; types)*
- **`create()` / `register()` validates and records a creation event; `fromSnapshot()` records nothing and throws on corrupted data.** Rebuilding from storage is not a business fact; corrupted storage is a programming error, not a refusal. *Fix:* Keep validation in the value objects so both paths re-run it; throw in `fromSnapshot()`, return a Result in `create()`. *(DOMAIN-CREATE-VS-RECONSTITUTE; tests)*
- **An aggregate generates its own identity (`Id.generate()` in `create()`). A repository loads and saves aggregates, and answers the facts a domain rule needs about the collection (`findByEmail`, `countByOwner`); it never hands out identities and never searches for a screen.** No persistence round-trip is needed to know who an object is, and the event of its creation can carry its id. *Fix:* Generate the Id in the factory; remove any "next id" method from the repository. *(DOMAIN-IDENTITY; review)*
- **Time is a parameter with a default; identity is generated by the domain; anything else that is not a function of the business state (randomness, a model, a person, another system) lives behind a port named for what it decides, and its result is a plain value the aggregate validates and may refuse.** The same state and command must give the same outcome; the source proposes, the domain disposes. *Fix:* Declare the port in the Application layer of the context, hand its result to the aggregate like any input, keep the provenance on the operation. *(DOMAIN-NON-DETERMINISM; review)*
- **Domain events are made durable with the state they describe, in the same transaction (the outbox), and published from there after the commit — never before, and never from memory alone; a rolled-back transaction stores nothing and leaves the events on the aggregate; a fact a crash kept from being published is published on the next relay, so a subscriber may see a fact twice and the bus delivers a message it already delivered once only; a reaction runs in a transaction of its own, and what it saves and what it publishes are made durable and published the same way.** Listeners must only ever see facts that are durable, and every durable fact must reach them; publishing from memory after the commit loses the facts a crash interrupts, so the facts are stored first and at-least-once delivery is paid for with idempotent delivery. *Fix:* Call `publishDomainEvents()`: it appends the aggregate's events to the unit of work's outbox at commit and the context relays the outbox after it; never publish from inside a behaviour; carry the entry's id as the message's id, and let the bus recognise it. In a reaction, the base handler opens the transaction: save, call `publishDomainEvents()` or `publishIntegrationEvent()`, and return a failed Result to undo all of it — never publish straight to the bus, and never make the reaction idempotent by hand. *(EVENT-AFTER-COMMIT; tests)*
- **Queries return read models, repositories return aggregates; never the other way.** The read side is free to be shaped for screens; the write side is where the rules live. *Fix:* Add a read-model shape to the queries port; never return an aggregate from a query, never a read model into a behaviour. *(QUERY-READ-MODELS; types)*
- **Contexts talk in two ways only — integration events published in the shared kernel, and ports the asking side owns, answered by an adapter over the other context's read model; a context's Domain never imports another context.** The contract between contexts must be a visible, versionable file, not a class that changes for its own reasons. *Fix:* Publish an integration event from a domain event handler and consume it through an anti-corruption handler; or declare a port in your words and adapt the other context's read model. *(CTX-CONTRACTS; linter)*
- **An aggregate carries the version it was read at and never changes it; `save()` stores version + 1 and refuses an aggregate that is no longer at the stored version with a ConcurrencyConflictException; the command handler then re-reads and re-decides in a new transaction, up to three attempts, and the third conflict is the operation's refusal.** A consistency boundary is only as good as the write; of two writers who read the same version only the first may win, and the second, re-run on what the first wrote, usually wins too — a rule re-decided on fresh state is a decision, a write re-applied blindly is not. *Fix:* Check the stored version in the adapter the way the store makes atomic (an UPDATE ... WHERE version = ?), return a failed Result; let the base handler retry `execute()` from a fresh read, and let the third conflict reach the client, who re-reads and decides. *(CONC-OPTIMISTIC; tests)*
- **Every file the concept map names exists, every documentation link resolves, nothing silences the linter, and the generated import rules refuse and allow what the probes say.** A reference whose map points at nothing teaches nothing. *Fix:* Run the conventions check; fix the file or the map, never the check. *(ARCH-MAP-IS-REAL; check)*
- **A newcomer, or an agent, can add a feature in the right shape from the documentation alone.** That is what a reference is for. *Fix:* Run a fresh-agent evaluation; every guess in its report is a sentence missing from the guide. *(ARCH-LEARNABLE; evaluations)*
- **Every language the reference is written in is held to this file — the same layers, the same rules under the same ids, the same HTTP grammar — through a binding that says where its trees are and which file shows each concept; a language never carries a rule of its own.** The architecture is one thing rendered in several languages; a second wording of a rule is a second thing to drift. *Fix:* Put the rule here and point the binding at the file that shows it; what a language cannot hold, it reports as a gap in its binding, not as a rule it lacks. *(ARCH-ONE-CONTRACT; check)*
- **Every language answers the same HTTP API — the same routes, status codes, body shapes and public names — so one black-box scenario, run against each server, passes unchanged; the public name of an operation is its intent or its fact without the suffix of its kind (`ShareNote`, `NoteShared`).** A reference in several languages teaches one application, not three; a client, a front end or a test that works against one server must work against the others, and the API is where that is visible. *Fix:* Fix the server that differs, never the scenario; a name that leaks a class suffix is stripped where the record is projected, not renamed on the bus. *(API-ONE-SURFACE; tests)*
- **Every relationship between two contexts is declared once in the context map, with the strategic pattern it follows, the mechanism that carries it and why; the contracts it carries are read from the code, and the check refuses a link in the code the map does not declare and a declared relationship nothing in the code carries, unless it is declared `planned` — decided before the code that carries it.** A context map drawn by hand and never checked is a wish; one read from the code alone is an inventory with no intent in it. Declaring the pair, the pattern and the reason, and deriving the contracts, keeps both honest, and makes a new relationship between two contexts a decision written down before it is merged. *Fix:* Add the relationship to `relationships` in the domain map with its pattern and its reason — declared `planned` when it is decided before the code that carries it — or remove the link in the code, if the coupling was not meant; never widen the check. *(CTX-MAP-DECLARED; check)*
- **Every language's tree says the same application, in words every language shares — the commands of each context with who may call them, their route, the aggregate they reach and the events it records; the queries; the domain events; the policies and what they publish or reach; the links between contexts; each language's tool writes that inventory from its own tree, and the check holds the inventories equal.** The scenario holds the servers to one API from the outside; the inventory holds the trees to one model from the inside. A command one language has and another lacks, or a policy that reaches different facts, is one application in three languages and something else in the fourth, and nothing a client sees would say so. *Fix:* Fix the tree that differs, never the inventory — a missing command, a route that differs, a policy that reaches other events is a divergence to close in the code; then regenerate the inventory with the language's tool and commit it. *(ARCH-ONE-APPLICATION; check)*

- **The architecture is data.** [`conventions/architecture.yaml`](conventions/architecture.yaml) is the table the import rules of every language are generated from and the list of every rule above; [`conventions/concepts.yaml`](conventions/concepts.yaml) is the vocabulary the map is rendered from; [`conventions/typescript.yaml`](conventions/typescript.yaml) is where TypeScript names its contexts and the files that show each concept (`yarn conventions:write` regenerates the documents). A new context goes in the binding; a new file worth pointing at goes in the binding; a new rule goes in the contract, and in no binding. None of them is edited to make a violation pass.

## Working at the root

- **A rule lives in the contract, under one id for every language**, never in a binding (ARCH-ONE-CONTRACT). A binding may point at the file that shows a rule, and say `review` for one its tooling cannot hold yet; it may not reword one, weaken one or add one.
- **A relationship between two contexts is declared in the domain map before the code carries it** (CTX-MAP-DECLARED): the pair, the pattern on each side, the mechanism, the reason. The check refuses a link the map does not declare and a declared relationship nothing carries; a new relationship is a decision, and a feature plan that crosses an undeclared pair is refused. A new consumer of an existing relationship changes nothing in the map: the contracts are read from the code.
- **A feature's model is decided in a storm before the code and held to it after** ([ADR 22](docs/adr/0022-the-storm-is-facilitated-and-the-code-is-held-to-it.md)): the `storm` skill facilitates the session, `conventions/storms/<feature>.yaml` is what it decided, `yarn architecture storm validate|--expect <file>` holds it to the contract and to the code, and the check holds every storm: done and carried, or not yet.
- **Every language's tree says the same application** (ARCH-ONE-APPLICATION): each tool writes its inventory (`yarn conventions:write`, `cargo run -p conventions -- inventory --write`, `uv run python -m tools.conventions inventory --write`, `go run ./tools/conventions inventory --write`), each check refuses a stale one, and the TypeScript check refuses two that differ. A difference is closed in the tree that differs, never in the inventory.
- **A binding's paths are relative to its own directory**; the loader makes them repository-relative. Links in the Markdown fields of a binding (`example`, `notes`, `see`) follow the same rule.
- **The shared documents name no language's file directly.** The root README's map is rendered; the ADRs may link into a language's tree when they discuss a concrete file, with a path from `docs/adr/` (`../../typescript/src/…`), and `yarn check:conventions` checks that every such link resolves.
- **Adding a language** is the recipe in the [README](README.md#adding-a-language): a directory, a binding listed under `languages`, a linter and a check generated from the table, a README and a CLAUDE.md with the generated blocks. The map shows what the language still owes; it is not required to show everything on its first day.
- **Changing the contract, the domain map or a binding** regenerates every language's documents: run `yarn conventions:write` at the root (it renders every language's README), then the conventions check of each language (`yarn check:conventions` at the root, `cargo run -p conventions` in `rust/`, `uv run python -m tools.conventions` in `python/`, `go run ./tools/conventions` in `go/`), before the change is done.

## Things to avoid

- A second wording of a rule, in a binding, a README or a language's guide. Point at the id.
- A path in the contract or the concepts: those files are language-neutral by construction, and the check refuses a file reference in them.
- A second package at the root, a workspace or a meta build. The root's `package.json` is the tooling and nothing else ([ADR 23](docs/adr/0023-the-tooling-lives-at-the-root-and-ships-as-a-package.md)); each language's toolchain stays its own, and nothing at the root builds a language.
- Moving a language's linter or check to the root to share it. The tooling at the root reads any binding because a binding is data; what walks a language's tree, holds its imports or writes its inventory is that language's business, and the root asks it (ESLint for `can-import`, each language's tool for its inventory).

## How this guide is tested

Periodically a fresh agent, with nothing but this repository, is handed a small feature request in one language and graded on whether it lands the right shape; what it guessed becomes a fix in that language's guide, or here. Protocol and records: [`docs/evaluations`](docs/evaluations/README.md).
