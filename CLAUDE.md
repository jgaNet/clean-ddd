# Working on this repository (guide for AI assistance)

This is a **reference implementation** of Clean Architecture + Domain-Driven Design in TypeScript. The goal is one canonical, simple example per concept, with the architectural rules enforced by tooling. Before changing anything, read the [README](README.md): it maps every concept to the file that shows it, and links the decisions in [`docs/adr`](docs/adr).

## Commands

```bash
yarn start:dev          # Fastify on :10000, Swagger at /v1/docs
yarn check:conventions  # the contract is sound and the tree, README and CLAUDE.md agree with it
yarn architecture inspect | rules | concepts | verbs | checklists          # the contract, listed
yarn architecture rule <ID> | concept <id> | verb <intent> | checklist <kind> | place <kind>
yarn architecture can-import <file> <specifier> [<file> <specifier> …]     # asks ESLint before you write the import
yarn architecture plan validate|explain <file>                             # a feature plan, checked against the contract
                                                                           # --json everywhere, for tools
yarn typecheck          # tsc --noEmit
yarn lint               # eslint, including the layer-boundary rules
yarn test:units         # unit tests
yarn test:e2e           # each suite boots its own application on a free port; no server to start
yarn test -- -t "name"  # one test
yarn format             # prettier (format:check is what CI runs)
```

Node ≥ 24 (`.nvmrc` = 24). All of `yarn check:conventions`, `yarn format:check`, `yarn lint`, `yarn typecheck`, `yarn test:units`, `yarn test:e2e` must pass before a change is done; CI runs them on every PR.

## Where things are

```
src/Bootstrap/Fastify/            composition root (createApplication.ts); application.ts is the entry point
src/Architecture/                 the building blocks: mechanics, no vocabulary (they do not even know the roles)
  Domain/                         Entity, AggregateRoot, ValueObject, Id, Event(+kinds), Exception, Result — depends on nothing
  Application/                    CommandHandler, QueryHandler, EventHandler, ExecutionContext, EventBus, Module, Application
  Infrastructure/                 InMemoryDataSource, InMemoryEventBus, InMemoryUnitOfWork, ConsoleLogger
  Presentation/                   Presenter, Format (json | htmx per request), the html tag
src/SharedKernel/                 the shared kernel, in the DDD sense: what every context agrees on
  Domain/                         Email, Role
  Application/                    Guards (requireSignedIn), IntegrationEvents/ (the contracts between contexts)
src/Contexts/<Context>/
  Domain/<Aggregate>/             aggregate, value objects, status, Events/, exceptions, DTOs (snapshot), Ports/
  Application/                    Commands/<UseCase>/, Queries/<UseCase>/, Events/, Services/
  Infrastructure/                 implementations of the ports
  Presentation/                   controllers, routes + schemas, presenters
  module.local.ts                 wiring
```

Path aliases: `@Architecture/*`, `@SharedKernel/*`, `@Contexts/*`, `@Bootstrap/*`. A relative import may only name a sibling file (`./NoteStatus`); anything across directories uses an alias. ESLint enforces it, because the boundary rules match on aliases.

## The rules (enforced)

Each rule has a stable id; `yarn architecture rule <ID>` explains it, `--json` for a tool. The list below is rendered from [`conventions/architecture.yaml`](conventions/architecture.yaml).

<!-- generated from conventions/architecture.yaml (rules); edit the YAML, then run yarn conventions:write -->
- **A relative import names a sibling file (`./NoteTitle`) and nothing else; anything across directories goes through an alias.** The import rules are written against the aliases; a relative path across directories would bypass them. *Fix:* Import through the alias (@Contexts/..., @Architecture/..., @SharedKernel/...). *(ARCH-RELATIVE; eslint)*
- **Dependencies point inward and contexts stay apart — each file imports only what its row of the dependency table allows; there is no exception and none may be added.** A boundary that can be crossed when convenient is not a boundary; the table is the architecture. *Fix:* Fix a violation with a port, an integration event or a move, never with an eslint-disable (the conventions check refuses one). *(ARCH-INWARD; eslint)*
- **The building blocks (@Architecture) import nothing outside themselves, not even the shared kernel; the shared kernel (@SharedKernel) imports the building blocks and no context.** The building blocks are mechanics and must know no vocabulary, not even the roles; the shared kernel is the part of the domain model every context agrees on, built on those mechanics. *Fix:* Vocabulary (a role, an email, a policy) goes to @SharedKernel; mechanics go to @Architecture; a context's things stay in the context. *(ARCH-TREES; eslint)*
- **Every directory under src/Contexts is a context declared in this file, holds only the declared layers and a module.local.ts.** An undeclared context has no import rule applying to it. *Fix:* Add the context to `contexts` above; move stray files into a layer. *(ARCH-CONTEXT-DECLARED; check)*
- **A context's wiring is one module.local.ts building `new Module({ name, commands, queries, domainEvents, integrationEvents })`; anything else it exposes is a named export of that file. No container, no builder, no service locator.** Wiring that is data can be read in one screen and explained to an agent; a container hides which handler answers which command. *Fix:* Construct the handler with `new`, pass its ports, list it in the Module. *(ARCH-MODULES-DATA; review)*
- **ExecutionContext carries what exists per request and nothing else — who is calling, the trace, the transaction, the bus, the logger. A mailer, a clock, a model client is a constructor dependency of the handler that needs it.** A context that grows is a service locator with a better name; a handler's needs belong in its signature. *Fix:* Add a port, inject it in the constructor, pass it from module.local.ts. *(ARCH-EXECUTION-CONTEXT; review)*
- **A refused command or query is a failed Result (`IResult<T>` in signatures, `Result.ok()` / `Result.fail(exception)`), never a thrown exception; `throw` is for programming errors and corrupted state only.** A refusal is a normal outcome the caller must handle; a throw is a crash that hides it. *Fix:* Return `Result.fail(new <Rule>Exception(...))` from the behaviour; let the handler pass it on; the base handler turns a stray throw into a failed operation. *(DOMAIN-RESULT; tests)*
- **Only an aggregate root records domain events (`this.record(...)` inside a behaviour); handlers never construct one, they call `publishDomainEvents(aggregate, context)` after saving.** The fact belongs to the object whose rule produced it; a handler that builds events can lie about what happened. *Fix:* Move the `record()` call into the behaviour that changes the state. *(DOMAIN-RECORDS-EVENTS; types)*
- **`create()` / `register()` validates and records a creation event; `fromSnapshot()` records nothing and throws on corrupted data.** Rebuilding from storage is not a business fact; corrupted storage is a programming error, not a refusal. *Fix:* Keep validation in the value objects so both paths re-run it; throw in `fromSnapshot()`, return a Result in `create()`. *(DOMAIN-CREATE-VS-RECONSTITUTE; tests)*
- **An aggregate generates its own identity (`Id.generate()` in `create()`). A repository loads and saves aggregates, and answers the facts a domain rule needs about the collection (`findByEmail`, `countByOwner`); it never hands out identities and never searches for a screen.** No persistence round-trip is needed to know who an object is, and the event of its creation can carry its id. *Fix:* Generate the Id in the factory; remove any "next id" method from the repository. *(DOMAIN-IDENTITY; review)*
- **Time is a parameter with a default; identity is generated by the domain; anything else that is not a function of the business state (randomness, a model, a person, another system) lives behind a port named for what it decides, and its result is a plain value the aggregate validates and may refuse.** The same state and command must give the same outcome; the source proposes, the domain disposes. *Fix:* Declare the port in the Application layer of the context, hand its result to the aggregate like any input, keep the provenance on the operation. *(DOMAIN-NON-DETERMINISM; review)*
- **Domain events are published after the transaction commits, never before; a rolled-back transaction publishes nothing and leaves the events on the aggregate.** Listeners must only ever see facts that are durable. *Fix:* Call `publishDomainEvents()` and let `ExecutionContext.afterCommit()` do the timing; never publish from inside a behaviour. *(EVENT-AFTER-COMMIT; tests)*
- **Queries return read models, repositories return aggregates; never the other way.** The read side is free to be shaped for screens; the write side is where the rules live. *Fix:* Add a read-model shape to the queries port; never return an aggregate from a query, never a read model into a behaviour. *(QUERY-READ-MODELS; types)*
- **Contexts talk in two ways only — integration events published in the shared kernel, and ports the asking side owns, answered by an adapter over the other context's read model; a context's Domain never imports another context.** The contract between contexts must be a visible, versionable file, not a class that changes for its own reasons. *Fix:* Publish an integration event from a domain event handler and consume it through an anti-corruption handler; or declare a port in your words and adapt the other context's read model. *(CTX-CONTRACTS; eslint)*
- **An aggregate carries the version it was read at and never changes it; `save()` stores version + 1 and refuses an aggregate that is no longer at the stored version with a ConcurrencyConflictException.** A consistency boundary is only as good as the write; of two writers who read the same version only the first may win. *Fix:* Check the stored version in the adapter the way the store makes atomic (an UPDATE ... WHERE version = ?), return a failed Result, let the caller re-read. *(CONC-OPTIMISTIC; tests)*
- **Every file the concept map names exists, every documentation link resolves, nothing silences ESLint, and the generated import rules refuse and allow what the probes say.** A reference whose map points at nothing teaches nothing. *Fix:* Run `yarn check:conventions`; fix the file or the map, never the check. *(ARCH-MAP-IS-REAL; check)*
- **A newcomer, or an agent, can add a feature in the right shape from the documentation alone.** That is what a reference is for. *Fix:* Run a fresh-agent evaluation; every guess in its report is a sentence missing from the guide. *(ARCH-LEARNABLE; evaluations)*
<!-- end generated -->

- **The architecture is data.** [`conventions/architecture.yaml`](conventions/architecture.yaml) is the table the import rules are generated from and the list of every rule above; [`conventions/concepts.yaml`](conventions/concepts.yaml) is the list of canonical files the README map is rendered from (`yarn conventions:write`). A new context goes in the first; a new file worth pointing at goes in the second. Neither is edited to make a violation pass.


## How to add a feature (follow an existing one, do not invent a shape)

The questions each step raises (verbs, barrels, where a spec goes, whether an event needs a handler) are answered in the next section; read it before starting.

Before writing: `yarn architecture checklist <aggregate | value-object | domain-service | command | query | context>` lists what a new one of each is made of and where it goes, and `yarn architecture can-import <file> <specifier> …` says whether a planned import will be allowed. For a change worth stating first, write a **feature plan** ([`conventions/plans/share-a-note.yaml`](conventions/plans/share-a-note.yaml) is the example) and run `yarn architecture plan validate <file>` — it refuses an undeclared context, an unknown kind, a route whose method contradicts its intent, a cross-context strategy that is neither an integration event nor an owned port, and anything new where something already exists — then `plan explain <file>` for the file list, the rules and the examples to copy.

1. **Domain first.** Add a behaviour to the aggregate that enforces the rule and records an event ([`Note.ts`](src/Contexts/Notes/Domain/Note/Note.ts)). A pure read changes nothing, so it skips the aggregate: its first step is a read model and a method on the queries port ([`INoteQueries.ts`](src/Contexts/Notes/Domain/Note/Ports/INoteQueries.ts)), then a query handler. New rule about the whole collection? A domain service ([`AccountRegistration.ts`](src/Contexts/Security/Domain/Account/AccountRegistration.ts)). New concept with validation? A value object ([`NoteTitle.ts`](src/Contexts/Notes/Domain/Note/NoteTitle.ts)) for one value; a rule about *several* values of one aggregate (at most five tags, no duplicates) is the aggregate's invariant, written once and used by `create()`, the behaviour and `fromSnapshot()`, not a second value object. One exception per rule the user could act on differently (`BlankNoteTitle` and `NoteTitleTooLong` are two; a format rule is one). A business constant is a `static readonly` on the class that enforces it (`NoteTitle.MAX_LENGTH`). A `create()` with nothing to validate may return the aggregate itself rather than a `Result`; say so in its doc comment. A thing with its own identity that lives only inside the aggregate, stays few, and must be consistent with it in the same change is a **child entity** ([`DeliveryAttempt.ts`](src/Contexts/Notifications/Domain/Notification/DeliveryAttempt.ts)); a thing that grows without bound, is written by other people than the root's owner, or need not be consistent with the root in the same transaction is **its own aggregate** that references the root by id, with a domain service when a rule spans both — at the cost that a rule over the collection ("one reaction per person per note") stops being an invariant the root enforces and becomes a check then a write, which needs the store's help (a unique key) to be airtight — comments on a note are the second kind, delivery attempts of a notification the first. Write the spec next to it.
2. **Command + handler**, copied from [`EditNoteCommandHandler.ts`](src/Contexts/Notes/Application/Commands/EditNote/EditNoteCommandHandler.ts): who is calling → load → ask the aggregate → save → `publishDomainEvents`. A command may leave a field optional when the domain has a default for it (a note starts untagged); the default belongs to the aggregate, not to the controller. Prefer a new command over widening a canonical one (`RetagNote` rather than tags in `EditNote`), so the example everyone copies stays small. Or a query handler from [`GetNoteQueryHandler.ts`](src/Contexts/Notes/Application/Queries/GetNote/GetNoteQueryHandler.ts). Test with the in-memory implementations as doubles ([`NoteCommandHandlers.spec.ts`](src/Contexts/Notes/Application/Commands/NoteCommandHandlers.spec.ts)).
3. **Infrastructure** only if a port changed. A new adapter of an existing port is added to the `adapters` list of its contract spec ([`NotePersistence.contract.spec.ts`](src/Contexts/Notes/Infrastructure/NotePersistence.contract.spec.ts)) and must pass it unchanged; that is the whole review. A port that has only one adapter gets its contract spec the day a method of it promises an order or a filter: the promise is on the port, so its test is written against the port, even with one entry in `adapters`.
4. **Route + controller method** ([`note.routes.ts`](src/Contexts/Notes/Presentation/API/REST/Routes/note.routes.ts)): commands answer `202 { operationId }`, queries answer synchronously. Add the JSON schema — and remember that Fastify serializes **only** the response fields the schema lists: a new read-model field without its schema line is silently dropped from the API. Schemas describe shape (`type`, `required`), not business rules: a bad tag is refused by the domain and shows up on the operation, not as a `400` from a `pattern`. An enum of allowed values is shape: list it from the domain enum (`enum: Object.values(AccountStatus)`), and a new value then needs no schema change. A value the body sends as a string reaches the command as a string; the domain turns it into the enum with a type guard (`isRole()`), never the controller. The HTMX pages are the presenters' example, not a second client to keep in parity: a new field does not oblige a new form control.
5. **Register** in `module.local.ts`. Add an e2e case if the flow is user-visible. Each e2e suite boots one application that its tests share, in order: write a case relative to what the earlier ones left (or with a fresh account), never assuming an empty store.
6. Cross-context reaction? Publish an integration event from a domain event handler ([`NoteSharedHandler.ts`](src/Contexts/Notes/Application/Events/NoteSharedHandler.ts)) and consume it through an anti-corruption handler in the other context ([`NoteSharedIntegrationEventHandler.ts`](src/Contexts/Notifications/Application/Events/NoteSharedIntegrationEventHandler.ts)).

## Questions you will have, answered once

- **Where does the spec go?** Next to the file it tests, same name plus `.spec.ts`. The handlers of one aggregate may share one spec when they share fixtures ([`NoteCommandHandlers.spec.ts`](src/Contexts/Notes/Application/Commands/NoteCommandHandlers.spec.ts)); otherwise one per handler ([`SignUpCommandHandler.spec.ts`](src/Contexts/Security/Application/Commands/SignUp/SignUpCommandHandler.spec.ts)). Every command handler has at least its happy path and one refusal in a spec; so does a query handler that holds a visibility or role rule. End-to-end suites sit with the routes, as `*.e2e.spec.ts`.
- **Does the read side's order matter?** Yes, and it belongs to the queries port: the order a method returns is written in its JSDoc ([`INoteQueries.ts`](src/Contexts/Notes/Domain/Note/Ports/INoteQueries.ts)) and asserted for every adapter by the contract spec. A query handler never sorts. A read model may join several stores in the adapter (a bookmark's list item carries the note's title): that freedom is what [ADR 5](docs/adr/0005-queries-return-read-models-not-aggregates.md) gives the read side.
- **Does a new exception need a line in `refuse()`?** No. `refuse()` maps *kinds*, not exceptions: `NotAllowedException` → `403`, the aggregate's not-found exception → `404`, anything else → `400`. A refused command never reaches `refuse()` at all: it is on the operation.
- **Does every domain event need a handler?** No. The aggregate records the fact because it happened; subscribe a handler only when something reacts to it. `NoteEditedEvent` has none: it is still recorded by the Tracker, and a handler can be added later without touching the aggregate.
- **Which HTTP verb?** `yarn architecture verb <intent>` answers from the table in the contract (`read`, `create`, `act`, `create-under`, `replace`, `replace-part`, `change-part`, `remove`). In short: `GET` for a query (never changes state). `POST` to create (`/notes`) and for a command that is an action on a thing (`/notes/:id/share`, `/notes/:id/archive`); `PUT /notes/:id` to replace its editable content, `PUT /notes/:id/tags` to replace one part of it, `POST /notes/:id/comments` to create one item under it, `DELETE /notes/:id/bookmark` to remove a thing the caller created and the URL identifies; `PATCH` for a partial state change (`/notifications/:id/read`). The two `GET …/validate` routes are commands on `GET` because they are links clicked from an email; do not copy that for anything else.
- **Barrels (`index.ts`)?** One per `Commands/` and `Queries/` folder, listing the events and handlers of the context; one per presenters folder; the `@Architecture` and `@SharedKernel` layers export their public surface through one (`Domain/index.ts`, `Application/index.ts`). No barrel per use-case folder, no barrel in `Domain/<Aggregate>/Ports/`; an import names the file otherwise.
- **An existing event needs more data for a new consumer?** Widen the domain event's payload in the aggregate, which holds the state; do not add a second event for the same fact. One fact is one message: a fact with several interested parties is one event carrying the list (`recipientIds`), and the fan-out is the consumer's business. A domain event needs no handler; an integration event exists only once a first consumer needs the fact, and from then on it is published whenever the fact happens, whether or not anyone listens, in the publishing context's public vocabulary rather than the aggregate's field names.
- **Do event handlers need a guard?** No. A domain or integration event handler reacts to a fact that was already allowed, in the publisher's context; authorization happened in the command that produced it. The base [`EventHandler`](src/Architecture/Application/EventHandler.ts) has no `guard()`.
- **A query about an id another context owns?** (Notes counting the notes of an *account*.) Answer from your own store for whatever id you are given, and say in the port's JSDoc what an unknown id gets (zeros, an empty list). A query handler has one port and existence is not its question; if a caller must know whether the account exists, that is Security's endpoint. The route stays under your context's prefix, with a static segment so it cannot collide with `/:id` (`GET /notes/accounts/:accountId/counts`).
- **Deleting an aggregate?** When the thing is truly gone (a bookmark removed) the repository has a `delete(aggregate)`, with the same version check as `save()`; the aggregate still decides — a behaviour (`remove(actorId)`) checks who may and records the fact, then the handler deletes. When the thing has a lifecycle (a note archived), it is a status and a `restore()`, not a delete.
- **How do I test a `guard()`?** Through `handle()`: the base class runs `guard()` before `execute()`, so a spec that calls `execute()` directly skips it. Build the operation the way the bus would, with an `InMemoryEventBus` ([`RegisterAdminCommandHandler.spec.ts`](src/Contexts/Security/Application/Commands/RegisterAdmin/RegisterAdminCommandHandler.spec.ts)). A rule written as `requireSignedIn()` inside `execute()` is tested through `execute()`, like the Notes command handlers.
- **A port to another context that returns more than a boolean?** Declare the shape in the port file, in your own words (`AccountPlan` next to its port), and translate in the adapter with a `switch` written out; never import the other context's enum or read model into your Domain. One port per answering context: an adapter reads one context, so a question for Billing is a second port (`IAccountPlans`), not a method on the port Security answers. The port carries the fact in the other context's terms (which plan); what the fact means here (how many notes) is this context's rule, in its domain service.
- **A default for an aggregate that does not exist yet?** (Every account is on the free plan until an administrator acts.) A constant on the aggregate (`DEFAULT_PLAN`), used by `create()` and answered by the queries port for an id with nothing stored; do not materialise one aggregate per account just to hold the default. Materialise (react to the other context's integration event) only when the fact itself must be recorded, with its date and its author.
- **The domain needs a fact about the whole collection?** (Does an email exist? How many notes does this account own?) That is a repository question (`findByEmail`, a `countByOwner`), because the rule is checked on the write side against what is saved; a number for a screen is a queries question. The rule itself goes in a domain service ([`AccountRegistration.ts`](src/Contexts/Security/Domain/Account/AccountRegistration.ts)).
- **A refusal that must leave a trace?** (A wrong password is counted towards a lockout.) Inside `handle()` a failed `Result` rolls the transaction back and drops the events (ADR 3), so never save on the failure path of a published command. The trace is a fact of its own: publish a command for it (`RecordFailedLogin`) before returning the refusal, and let its handler load, count, save and publish in its own transaction. Login runs `execute()` directly (the caller needs the token), so there the simpler shape — save, then refuse — happens to hold; if you rely on that, say so in a comment. There is no canonical example of this yet (README, *Known gaps*).
- **New aggregate in this context, or a new context?** A new context when the words change meaning (an *account* in Security is a *recipient* in Notifications), when it has its own reasons to change or its own owners, and when you could deploy it alone with nothing but integration events (and ports) between it and the rest. Test it on the nouns of the request, not on which existing thing they attach to: *plan*, *quota* and *pricing* mean nothing to "who can sign in", change when the business model changes, and could ship alone — that is a Billing context, which Notes asks through a port exactly as it asks Security today, even though the request says "an account's plan". *Pin*, *tags* and *comments* are Notes: same words, same reasons to change. Otherwise it is an aggregate (or a value object) in the context that already speaks its language; when the nouns are genuinely the same, stay: splitting later is a move, merging later is a rewrite.

## Code style

- Strict TypeScript; no `any`; every declared variable and parameter is used (`noUnusedLocals` / `noUnusedParameters`); `_` prefix for intentionally unused parameters.
- PascalCase for types and classes, camelCase otherwise, `I` prefix for ports (`INoteRepository`), suffixes `CommandEvent`, `CommandHandler`, `QueryHandler`, `Event`, `Exception`. A file is named after the class it exports (`FastifyNoteController.ts`), a folder after its use case (`RegisterAdmin/`).
- One `<Aggregate>Exceptions.ts` per aggregate, each exception with a PascalCase `type` (`'InvalidCredentials'`) and the context as `service`. Enum values are their UPPERCASE names (`AccountStatus.PENDING = 'PENDING'`). Factories are `create()`; a reconstitution is `fromSnapshot()`.
- Controllers all have the shape of [`FastifyNoteController.ts`](src/Contexts/Notes/Presentation/API/REST/Controllers/FastifyNoteController.ts): a command is published and answered `202 { operationId }`; a query's failure goes through one private `refuse()` (`403` for `NotAllowedException`, `404` for a not-found exception, `400` otherwise, body `{ message }`). No `try/catch` in a controller: handlers never throw an expected failure.
- Only [`ConsoleLogger.ts`](src/Architecture/Infrastructure/Logging/ConsoleLogger.ts) writes to the console; everything else logs through `context.logger` or the injected `Logger`.
- Doc comments explain *why* a file exists and what rule it protects, in a few lines. No commented-out code. No constructor that only calls `super()`.
- Prettier formats; do not fight it.
- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`), one concern per PR, and the PR body states how it was verified.

## Things to avoid

- A generic `Mapper`, `Repository<T>`, `Saga`, service locator or DI container. They were removed on purpose.
- A second copy of an example. If a concept already has its canonical file, point to it. This is about what the README's map names, not a cap on using a pattern: a second domain service that asks a port is a second use, not a second example.
- Exposing internals through a read model (no credentials, no execution context in an API response).
- Fixing a boundary violation with an `eslint-disable` instead of a port.
- A sixth member on `ExecutionContext`. It carries what exists per request and nothing else: who is calling, the trace, the transaction, the bus that carries the context along, the logger that stamps the trace. A mailer, a clock, a model client, a cache are constructor dependencies of the handler that needs them, visible in its signature; a context that grows is a service locator with a better name.

## How this guide is tested

Periodically a fresh agent, with nothing but this repository, is handed a small feature request and graded on whether it lands the right shape; what it guessed becomes a fix here. Protocol and records: [`docs/evaluations`](docs/evaluations/README.md).
