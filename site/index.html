What it is

One architecture, rendered in four languages

Every Domain-Driven Design and Clean Architecture concept appears exactly once, in the simplest form that still does its job. The rules are checked by tooling, in every language, under the same ids.

One small application

Notes you can share, accounts, notifications, the tracking of every operation. The business is small on purpose: the point is the shape.

Four languages, one architecture

TypeScript, Rust, Python and Go, each in its own directory with its own toolchain. The same layers, the same rules, the same HTTP API.

The architecture is data

The layers, who may import whom, every rule under a stable id, the HTTP grammar: a YAML contract the import rules of every language are generated from.

Rules held by tooling

A linter generated from the table, a conventions check, the compiler and the tests. A boundary that can be crossed when convenient is not a boundary.

Decided in a storm, held in the code

A feature’s model is decided in a facilitated event-storming session, written down, and the code is held to it until nothing is owed.

Measured with AI agents

Two benchmarks ran coding agents with and without the architecture, against hidden tests, and wrote down what it buys and what it costs.

Measured

What it buys, and what it costs

The repository was built on a bet: an architecture made explicit and enforced makes AI agents better at building software. The bet was then measured, in two benchmarks, against hidden acceptance tests no agent saw.

32
agent runs graded against hidden tests, in six experiments on the notes application
1.4–2.8×
the plain project’s time, taken by the architecture arms in each experiment
3.1–6.0×
the plain project’s cost, in each experiment
0
domain files the move to SQLite touched in the architecture trees

It does not make an agent faster or better.

In every experiment the plain project delivered as much, sooner and cheaper; a weaker model was not helped either. A lodging marketplace built to fifty features said the same, and toward a hundred every tree stopped on a rule nobody had written down.

It buys four things, each measured.

Changes stay in their layer. Fewer defects the tests cannot see, in the money. A structure that does not drift, with the tooling. And several agents on one codebase, one per bounded context, without conflicts.

So the project is offered as a guardrail and a coordinator for agents, not as an accelerator. Every number, log and grade is in the repository, and the article reads them from there.

Concepts

Every concept, once, in each language

The vocabulary is data too. Each concept names its rules and its decisions, and each language’s binding names the one file that shows it. The map says what a language still owes.

Aggregate root

Generates its own identity, records its own events inside a behaviour, carries the version it was read at.

Value object

Validates once and is reused by both paths: create() returns a refusal, fromSnapshot() throws on corrupted data.

Domain event

A fact an aggregate recorded, made durable with the state in the same transaction and published after the commit.

Integration event

The contract between two contexts, published in the shared kernel in the public words of the context that announces it.

Command and query

A command has exactly one handler and is answered later; a query returns a read model shaped for a screen, never an aggregate.

Result, not exception

A refused command is a failed Result carrying the rule’s exception; a throw is for programming errors only.

Outbox

Events are stored with the state and relayed after the commit, so a listener only ever sees facts that are durable.

Optimistic concurrency

save() stores version + 1 and refuses a stale aggregate; the handler re-reads and re-decides, up to three attempts.

Ports and adapters

Anything that is not a function of the business state lives behind a port named for what it decides.

Context map

Every relationship between two contexts is declared once, with its pattern, its mechanism and why; the check holds it to the code.

Policy

A reaction to a fact, in a transaction of its own; a second reaction to the same intent, never a second handler.

Two modes of work

A feature stays inside the architecture; a change to the architecture is a decision, with the ADR that explains it.

The domain, the storm, the inventory

The context map with its contracts read from the code, the event storm and its board, what each tree says the application is.

yarn architecture
$ yarn architecture rule ARCH-INWARD
ARCH-INWARD (dependencies-point-inward) — enforced by linter
Dependencies point inward and contexts stay apart — each file
imports only what its row of the dependency table allows;
there is no exception and none may be added.
Why:
  A boundary that can be crossed when convenient is not a
  boundary; the table is the architecture.

A feature is decided first, then held

A storm before the code

The facts first, then who asks for them, what decides, what reacts, what a screen needs. What the session decided is written down, in words every language shares.

A checklist for every kind of thing

What a new command is made of and where it goes, with the canonical file to copy, in the language you write.

Two modes, enforced

The feature mode refuses a change to the building blocks, the shared kernel, the conventions or the decisions. The architecture mode asks for the ADR.

a feature, end to end
$ yarn architecture storm --expect conventions/storms/share-a-note.yaml
share-a-note (done): The owner of a note shares it with another
account, which can then read it, and the people a note is shared
with are told about it.
The code carries the storm: the typescript inventory is the expected one.

$ yarn architecture checklist command --language rust
A new command goes in rust/src/contexts/<context>/application/
  src/commands/<use_case>.rs

- The handler in the same file …
Canonical example:
  rust/src/contexts/notes/application/src/commands/edit_note.rs

Every tree says the same application

One API, one scenario

A black-box client of 32 steps walks whichever server is up and passes against each: the same routes, status codes, body shapes and public names.

One inventory, held equal

Each language’s tool writes what its tree says the application is; the check refuses two that differ. A difference is closed in the tree, never in the inventory.

A map that is real

Every file the concept map names exists, every link resolves, nothing silences the linter, and the generated import rules refuse and allow what the probes say.

Languages

Run it, in the language you read best

Every server listens on the same port and answers the same API under /v1. Each language has its own README, where the request is followed end to end, and its own guide for working in it, by hand or with an agent.

TypeScript

Run the server

cd typescript && yarn install && yarn start:dev

Hold it to the architecture

yarn check:conventions && yarn lint && yarn test:e2e

Rust

Run the server

cd rust && cargo run -p bootstrap

Hold it to the architecture

cargo run -p conventions && cargo clippy && cargo test

Python

Run the server

cd python && uv sync && uv run python -m bootstrap

Hold it to the architecture

uv run python -m tools.conventions && uv run pytest

Go

Run the server

cd go && go run ./bootstrap/cmd/application

Hold it to the architecture

go run ./tools/conventions && go test ./...
