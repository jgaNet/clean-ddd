Does Clean Architecture help an AI agent write software?

We built a reference implementation of Clean Architecture and Domain-Driven Design whose rules are data, a tool that holds code to them, and a flow that lets several agents build features in parallel. Then we measured whether any of it helps an agent deliver. On our benchmark, it did not.

30 October 2026 · The clean-ddd experiments · Every number below is read from the records in the repository.

The short answer. A coding agent given a plain TypeScript project delivered the same seven features, and passed the same hidden acceptance tests, as an agent given Clean Architecture, DDD and our tooling. It was about 2.5 times sooner and 4.2 times cheaper. It also took the largest change of the benchmark sooner and cheaper. Two independent readers found no difference in quality between the trees.

Our tool does what it claims: it holds code to the architecture exactly, and it made a parallel fan-out of agents safe where naive parallelism failed. On this benchmark neither bought anything a plain single agent did not already deliver.

The limits of this answer: it is one model, one small backlog, in-memory infrastructure, a handful of runs, and graders who are agents.

What we built

clean-ddd is a reference implementation of Clean Architecture with DDD, in four languages. The architecture is data: layers, who may import whom, and every rule under a stable id live in YAML files. Linters, a conventions check and the documentation are generated from them. Around it we built the tooling an AI agent would use:

  • a gate: one verdict on whether a change stayed inside the architecture;
  • expected event storms, which hold the code to the model a feature was decided to have;
  • a checked context map, which refuses a coupling between two contexts nobody declared;
  • a multi-agent flow: one agent per bounded context, against a frozen contract, integrated by a single writer.

The bet was that an architecture made explicit and enforced would make AI agents better at building software, alone and together. This article is the test of that bet.

How we measured

A backlog of seven features of a notes application, from accounts and notes to sharing, notifications, a plan with a quota, and reminders. Each feature was written in product words, with the HTTP API it must answer. For each feature, a black-box acceptance test over HTTP was written before any run, and no agent ever saw it. The same model, through the same headless runner, built the backlog in every arm. Each arm's starting point and instructions differed:

1. Everyone delivered

All 11 runs passed all seven hidden acceptance tests, on every arm. Correctness, as a client sees it, did not separate the arms at all.

4. The large change did not favour the architecture

Feature 8 adds team spaces to the finished application: members, roles, invitations, seats, search and an audit trail, across six contexts, three of them new. We predicted, before the runs, that if the architecture pays anywhere, it is here. One fresh agent took it on one finished tree of each arm. C′ ran six agents in parallel.

5. What the tests cannot see

Black-box tests do not see where a rule lives, whether a password is hashed, or how far a change spreads. Two agents that had not run the benchmark read all eight trees, under neutral names, against a rubric written before the reading. The rubric's seven items apply to any structure:

  • passwords;
  • the owner taken from the caller;
  • each rule in one place;
  • refusals as outcomes;
  • injectable time;
  • parts that change apart;
  • rules under test.

On this proxy, changes were more local in the plain trees. A layered change spreads across more, smaller files: a domain object, a handler, a port, an adapter, the wiring, and their tests. Finding them meant reading about twice as many lines.

The readers' security findings went both ways:

  • The plain trees' login tokens never expire. The architecture trees sign theirs and expire them.
  • One architecture tree signs tokens with a fixed fallback secret. The agent copied that pattern from our own reference, which has the same fallback. It is a defect we will fix.

6. Is our tool relevant?

We separate what it did from what it bought.

  • It holds the architecture exactly. No production import crossed a boundary in any A tree. Without the tool, D's two trees had 0 and 20 refusals, all of the 20 in tests or in the form of an import, none in production code. A strong model, told the rules in prose, kept them nearly as well. The enforcement was real; what it prevented here was small.
  • Its storms and context map are ceremony a single agent pays for. In A's transcripts, most of what the tool caught was its own bookkeeping: a storm not marked done, a document to regenerate, a context missing from the map. It caught one substantive thing: a later feature reshaped an earlier command, and the storm check said so.
  • It made a parallel fan-out work. Naive parallel agents lost three of seven features to conflicts in one context. With the context as the conflict key, a frozen contract and one integrating writer, every feature landed. On the six-context feature, that fan-out was 21% sooner than one agent on the architecture, at 1.7 times the cost. It was still slower than one agent on a plain project.
  • Its strategy command recommends one agent unless a feature is wide and its time matters more than its cost. That rule is right as far as it goes. It should now also say that a small backlog does not need the architecture at all.

Our verdict: on work like this backlog, the tool is relevant as a coordination layer for several agents and as an enforcement layer for teams that have already chosen this architecture. It is not a productivity aid for a single strong agent, and choosing Clean Architecture with DDD for an AI agent's sake is not supported by these results.

7. How this fits what others found

The results agree with most of the literature we reviewed (related work):

  • Strong models conform to an architecture given as prose: a hexagonal pilot found 0% forbidden imports for a frontier model, against 80% for a small one.
  • Stacking Clean Architecture constraints on agents costs correctness points rather than adding them.
  • Repository instruction files are followed but rarely raise task success.
  • Multi-agent systems beat a strong single agent only on work that decomposes cleanly.

Our contribution is the control: the same backlog, the same model and the same hidden tests, with and without the architecture, and with and without the tool that enforces it.

8. What this does not show

  • A long horizon. Eight features and about four thousand lines are small. Architectural decay grows with code size, and this backlog never got big enough to suffer from it.
  • Real infrastructure. Every adapter was in memory. The transactional outbox, optimistic concurrency and retries the architecture provides were never exercised.
  • Weaker models, for which architecture documentation helps most.
  • People. Agents read the code here, not developers who must maintain it for years.
  • Independence. One person designed the architecture, the benchmark and the rubric, and agents graded the trees. The API's asynchronous protocol came from the architecture, which, if anything, favoured it.
  • Sample size. Three runs of A and P, two of D, and one per arm on feature 8.

Any of these could change the answer. They are the next experiments: a backlog of fifty features, real persistence, a weaker model, and a human maintainer timed on the change probes.
