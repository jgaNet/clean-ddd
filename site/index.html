Does Clean Architecture help an AI agent write software?

We built a reference implementation of Clean Architecture and Domain-Driven Design whose rules are data, a tool that holds code to them, and a flow that lets several agents build features in parallel. Then we measured whether any of it helps an agent deliver, including where it should help most: a weaker model, a growing codebase, a change of storage. On our benchmark, it did not. It did keep changes in their place, and only the tool kept the structure from drifting.

30 October 2026 · The clean-ddd experiments · Every number below is read from the records in the repository.

The short answer. A coding agent given a plain TypeScript project delivered the same seven features, and passed the same hidden acceptance tests, as an agent given Clean Architecture, DDD and our tooling. It was about 2.5 times sooner and 4.2 times cheaper. It also took the largest change of the benchmark sooner and cheaper. Two independent readers found no difference in quality between the trees.

Our tool does what it claims: it holds code to the architecture exactly, and it made a parallel fan-out of agents safe where naive parallelism failed. On this benchmark neither bought anything a plain single agent did not already deliver.

Then we tested where the architecture should pay. Four more experiments, written down before they ran, each took a condition the first answer could not rule out:

  • A weaker model. The plain project still delivered everything, and the architecture did not help.
  • Five more features on grown trees. Every arm kept delivering, and the plain project stayed the soonest.
  • A move to real storage. In the architecture trees the change stayed out of the domain, as promised, yet it still took twice as long as in the plain project.
  • The fan-out's contract given to one agent. It did not make that agent sooner: the fan-out's speed is its parallelism.

In every experiment that had a plain arm, the architecture arms took 1.4–2.8 times the plain project's time and 3.1–6.0 times its cost. What the architecture did buy is now measured: changes kept in their layer, and, with our tool only, a structure that does not drift as the code grows.

The limits of this answer: one model family, one application of twelve features, a handful of runs, and graders who are agents.

What we built

clean-ddd is a reference implementation of Clean Architecture with DDD, in four languages. The architecture is data: layers, who may import whom, and every rule under a stable id live in YAML files. Linters, a conventions check and the documentation are generated from them. Around it we built the tooling an AI agent would use:

  • a gate: one verdict on whether a change stayed inside the architecture;
  • expected event storms, which hold the code to the model a feature was decided to have;
  • a checked context map, which refuses a coupling between two contexts nobody declared;
  • a multi-agent flow: one agent per bounded context, against a frozen contract, integrated by a single writer.

The bet was that an architecture made explicit and enforced would make AI agents better at building software, alone and together. This article is the test of that bet.

How we measured

A backlog of seven features of a notes application, from accounts and notes to sharing, notifications, a plan with a quota, and reminders. Each feature was written in product words, with the HTTP API it must answer. For each feature, a black-box acceptance test over HTTP was written before any run, and no agent ever saw it. The same model, through the same headless runner, built the backlog in every arm. Each arm's starting point and instructions differed:

5. What the tests cannot see

Black-box tests do not see where a rule lives, whether a password is hashed, or how far a change spreads. Two agents that had not run the benchmark read all eight trees, under neutral names, against a rubric written before the reading. The rubric's seven items apply to any structure:

  • passwords;
  • the owner taken from the caller;
  • each rule in one place;
  • refusals as outcomes;
  • injectable time;
  • parts that change apart;
  • rules under test.

  • One architecture tree signs tokens with a fixed fallback secret. The agent copied that pattern from our own reference, which has the same fallback. It is a defect we will fix.

6. Is our tool relevant?

We separate what it did from what it bought.

  • It holds the architecture exactly, and the gap grows with the code. No import crossed a boundary in any A tree. Without the tool, D's trees had 0 and 20 refusals after the backlog, none in production code. Five features later, D's grown tree had 24. A model told the rules in prose keeps them nearly, not exactly, and the difference accumulates. The weaker model kept them as well as the strong one: 2 and 0 refusals.
  • It holds what the contract says, no more. With the weaker model, one A run answered an unknown plan with a 400 from its request schema, where the request wanted a refusal on the operation. Our own guide called a list of allowed values "shape", so the agent followed it and the gate rightly passed it. The gap was in the contract, and ADR 32 has since closed it: a command's body is refused for its shape only.
  • Its storms and context map are ceremony a single agent pays for. In A's transcripts, most of what the tool caught was its own bookkeeping: a storm not marked done, a document to regenerate, a context missing from the map. It caught one substantive thing: a later feature reshaped an earlier command, and the storm check said so.
  • It made a parallel fan-out work. Naive parallel agents lost three of seven features to conflicts in one context. With the context as the conflict key, a frozen contract and one integrating writer, every feature landed. On the six-context feature, that fan-out was 21% sooner than one agent on the architecture, at 1.7 times the cost. Giving one agent the same contract did not make it sooner (E2), so the gain is the parallelism, and the contract is what makes the parallelism safe. It was still slower than one agent on a plain project.
  • Its strategy command recommends one agent unless a feature is wide and its time matters more than its cost. That rule is right as far as it goes. It should now also say that a small backlog does not need the architecture at all.

Our verdict: the tool is relevant in two places. It coordinates several agents working in parallel. It enforces the architecture for teams that have already chosen it, and the longer they work, the more it matters. It is not a productivity aid for a single agent, strong or weak. Choosing Clean Architecture with DDD for an AI agent's sake is not supported by these results. Choosing it for what it does to the code — changes kept in their layer — is a choice these results can price: about twice the agent's time.

7. How this fits what others found

The results agree with most of the literature we reviewed (related work):

  • Strong models conform to an architecture given as prose: a hexagonal pilot found 0% forbidden imports for a frontier model, against 80% for a small one. Here the smallest model of the family conformed almost as well as the strong one. Its prose-only trees had 2 and 0 refusals, so this gap may depend on the model family more than on size.
  • Stacking Clean Architecture constraints on agents costs correctness points rather than adding them.
  • Repository instruction files are followed but rarely raise task success.
  • Multi-agent systems beat a strong single agent only on work that decomposes cleanly.

Our contribution is the control. The same backlog, the same model and the same hidden tests were run with and without the architecture, and with and without the tool that enforces it. Four further tests followed, each on a condition where the architecture is claimed to pay.

8. Four more experiments

The control named what it could not show. We wrote four more experiments, with their predictions, before running them (the protocol). Same driver, same grader, hidden tests no agent saw. Grading found three defects in our own kit, all recorded as amendments and applied to every tree alike.

The architecture did not help the weaker model deliver, and the weaker model paid relatively more to read it: about 6.0 times P's cost, against 4.2 times with the strong model.

E2. Was the fan-out's speed its contract?

On feature 8, the fan-out C′ was 21% sooner than one agent. But C′ also had a contract stage: a plan per context, frozen events and read models, and the acceptance test. We gave one agent all of it, from the same commit.

9. What this still does not show

  • A product's lifetime. Twelve features are still small. E3's direction needs several trees and many more features to become a result.
  • Concurrency and crashes under test. The outbox and the optimistic concurrency now run on real storage, but no test makes two writers race or kills the server between a commit and a publication.
  • People. Agents read the code here, not developers who must maintain it for years. The locality E4 shows matters to a reviewer; we did not price it.
  • Another model family. The weaker model was the smallest of the same family.
  • Independence. One person designed the architecture, the benchmark and the rubric, and agents graded the trees. The API's asynchronous protocol came from the architecture, which, if anything, favoured it.
  • Sample size. Two or three runs per arm, and one tree per arm in E3.
