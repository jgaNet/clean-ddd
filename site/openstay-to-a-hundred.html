OpenStay: to a hundred, and what it took

No OpenStay tree had reached a hundred features: J5 stopped every one, each where a rule was implicit. J5b ran requests 51 to 100 again on one tree per arm, with every rule J5 had found written down from the first request, the Clean DDD tree split between one agent per context. Both trees reached a hundred. What that took, and what it cost, says more about where AI-written software breaks than about which architecture wins.

13 November 2026 · The clean-ddd experiments · Every number below is copied from J5b's record and its logs.

The short answer. Both trees reached a hundred.

  • The plain tree was 3.7 times cheaper: $42.37 against $156.03.
  • It also delivered more requests at the first step: 47 of 50 against 39.
  • Three requests failed at every step, and none failed on a boundary between contexts. Each failed where a request had set a rule that nothing executable held:
    • the shape of an error;
    • null in a later state;
    • the time.
    Stating the rule once, in the tree's guide, let each through.
  • Splitting the Clean DDD tree's requests between one agent per context was safe, and bought nothing we could measure.

Where the trees stood before is the OpenStay article; the first benchmarks are the control and four more experiments.

Where J5 left it

J5 took six trees, three per arm, toward request 100. Every tree stopped, at 51 to 73, each on a seam where a rule the application needed was implicit:

  • an id given again in the next context;
  • an anonymous command answered 202;
  • a read that lapsed what it read;
  • a refusal answered 503.

Stating each rule let the trees through; the furthest of each arm reached 85, and none a hundred. Then the machine and its trees were lost.

The protocol

J5b's protocol was written before any run.

  • One tree per arm, the two that went furthest: simple-3 (a plain TypeScript project) and clean-3 (a project our tool created, held to its gate). Both started from their heads at request 50.
  • Every rule J5 found, from the first request, as sections of each tree's guide. The Clean DDD tree also had the kit J5 ended with: identity born once, a relationship between two contexts tested end to end, and the caller refused at once.
  • The ladder: each request starts with the smallest model and goes one step up when its hidden tests or its checks fail. A failure is replayed alone before it counts.
  • One repair per failure. When a request fails at every step, its failure is judged against the requests. The tree's guide then gains one section stating the rule it broke, never a test's answer, and the request is replayed. The section can be reworded once; a second failure after that stops the tree.
  • The Clean DDD tree's 14 requests that cross contexts were split: one agent per context, the upstream one writing the contract first, and an integrator that merges, runs the gate on the result and hands each failure to its owner.

What it cannot show:

  • It is in sample: every rule was written after seeing failures on these same requests.
  • It has one tree per arm.
  • The Clean DDD tree is both the architecture and the split.

  • The plain tree finished first and cheaper:

    • a request took 60 minutes on average, from the moment it was given to its delivery.
  • The Clean DDD tree finished a day later:
    • at $156.03, 87 minutes a request;
    • at a hundred, 56,834 source lines against 18,458;
    • 14 contexts kept apart, and 99 decision records written along the way.
  • The gap is mostly the cost of failing, not of writing. On a first attempt with the smallest model and one agent, the Clean DDD tree cost $0.66 against $0.49, about 35% more. The rest of the gap comes from what follows a failure: an escalation to a larger model, a split, a request failed at every step.
  • One request took both trees to the strongest model, on the same hidden test: a calendar import must leave the host's own blocks apart and take nothing from a booking.

Three failures, three seams

As J5b's repairs record them:

  • clean-3, request 61.
    • The failure: an operation's error read { type, message }, the shape the reference architecture gives it. The request says "<NAME>", the rule's name alone.
    • The repair: a section saying that the shape a request gives wins over the code's habit. It held once reworded.
  • simple-3, request 73.
    • The failure: a lapsed booking's payment read null, where an earlier request makes it null only for a booking still waiting.
    • The repair: a section on what null means. The first wording failed; the second held.
  • clean-3, request 73.
    • The failure: the sweep that lapses unpaid bookings took the machine's time. The rest of the tree took the clock the tests move, so the sweep saw no deadline passed.
    • The repair: a section saying the application has one now. It held at the first wording.

None of the three is a boundary crossed. In both arms, a request set a rule early; nothing executable held it where it was born; a late request needed it. That is J5's pattern again, at the seams J5's rules had not named.

The architecture took two of them in:

  • an operation's shape when read is now in its contract (ADR 41);
  • one clock, passed from the wiring, is a rule its linter holds in four languages (ADR 42).

  • It was safe. The integrator passed 24 merged results of 25, in 46 rounds.
  • Where the split failed at every step, one agent with the strongest model failed too, on the same rule (0 of 2 delivered).
  • It cost more and took longer: $6.19 a request against $1.93, and still $2.45 without its three costliest requests. The owners' agents cost $78.64, half the tree's total, for 14 requests of 50.
  • Half the owners' own verdicts failed (28 of 56), most of them because the other owner had not yet written its part. Each sent an agent back for a turn that could not fix it.
  • The ladder's own estimate recommended one agent on all 80 requests it was asked about. These requests were small, under the size where writing in parallel saves more than the contract and the integration cost.

Nothing here measures the split on a feature large enough to pay. The ladder now splits only where its estimate recommends it.

The bench

Grading had grown as long as writing. Each request's hidden tests and every earlier request's ran one file at a time, 25 to 40 minutes by request 80. A parallel grader runs them in one process, two at a time, and runs a file that fails there again alone. It was validated on both trees before it was used:

clean-3 was graded that way from request 86 on: 10 to 11 minutes a grading, no file run again alone. The plan records the change, and the record reports clean-3's times in two parts.

The machine intervened, and changed no verdict (the incident log):

  • 3 container restarts, each costing one attempt;
  • a resumed run that waited 2 hours for a machine slot its own reused process id held, now fixed in the harness;
  • a disk down to 1.4 GB;
  • one escalation on formatting alone, the kind of bookkeeping a tool should do instead of an agent.

What J5b adds

  • With the rules written down from the start, both arms reach a hundred. What stopped J5's trees was not the size of the code. It was rules no one had written, and those can be.
  • The failures that remain are at the specification, in both arms. A shape, a meaning, a time: things a request decides, that tests and contracts could hold where they are born. More layers would not have held them.
  • The architecture's cost is mostly the cost of its failures, not of its first attempts. A first attempt costs about a third more; escalations and splits make the rest.
  • The architecture's benefits did not show here, because nothing tested them. Its contexts stayed apart, and no change came unannounced. That is the measure the next campaign makes its first.

What this still does not show

  • Out of sample. Every rule was written after seeing these requests fail. The next campaign runs three arms (plain, a lighter Clean DDD profile, and the full one) on an application written before any run, which no rule was tuned on (its protocol).
  • Variance. One tree per arm; in J5, trees of one arm stopped 13 requests apart.
  • Whether the structure pays on change. No change was unannounced in requests 51 to 100.
  • Independence. One person designed the architecture, the benchmark and the repairs, with an AI assistant that also ran the bench and, for one night, judged clean-3's second failure as the maintainer had delegated it.
