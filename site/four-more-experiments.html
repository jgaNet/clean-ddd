Where the architecture should pay: four more experiments

The first benchmark said that Clean Architecture and DDD did not help an AI agent deliver a small application, and named what it could not show. Four experiments, each written down with its prediction before it ran, took one condition the architecture is claimed to pay under: a weaker model, a growing codebase, a change of storage, and the fan-out's contract given to a single agent.

30 October 2026 · The clean-ddd experiments · Every number below is read from the records in the repository.

The short answer. None of the four conditions turned the first answer around. The plain project still delivered everything with a weaker model, stayed the soonest as the trees grew, and took the move to real storage in half the architecture's time. The fan-out's contract, given to one agent, did not make it sooner: the fan-out's gain is its parallelism. What the architecture did buy is measured here: the storage change stayed out of the domain, and only the tool kept the structure from drifting.

The arms, the hidden tests and the grader are those of the first benchmark: A is the architecture with our tool, D the architecture as prose, P a plain TypeScript project, C′ the fan-out by context.

The protocol

The control named what it could not show. We wrote four more experiments, with their predictions, before running them (the protocol). Same driver, same grader, hidden tests no agent saw. Grading found three defects in our own kit, all recorded as amendments and applied to every tree alike.

E1. A weaker model

The literature finds that architecture documentation helps weaker models most. We ran the backlog with the smallest model of the same family, two runs per arm.

The plain project delivered 7/7 twice, in 19.4–22.4 minutes for $0.55–0.88. The architecture with the tool delivered 6/7 and 7/7 in 48.4–56.5 minutes. Its one failure is a 400 from the request schema, where the request wanted a 202 and a refused outcome. Our own guide then told the agent to put the list of allowed values in the schema. That was a gap in the architecture, since closed, not a slip of the agent. The architecture did not help the weaker model deliver, and the weaker model paid relatively more to read it: about 6.0 times P's cost, against 4.2 times with the strong model.

E2. Was the fan-out's speed its contract?

On feature 8, the fan-out C′ was 21% sooner than one agent. But C′ also had a contract stage: a plan per context, frozen events and read models, and the acceptance test. We gave one agent all of it, from the same commit.

With the whole contract, one agent took 22.5–24.8 minutes, as long as without it. The fan-out's gain was parallelism, not the contract. The contract is what makes the parallelism safe; on its own it bought nothing measurable.

E3. Five more features

Architectural decay is said to grow with code size. One finished tree per arm took five more features that change what exists: comments, a note's history with a restore, editors on a shared note, deleting an account and everything it owns, and search.

Every arm passed every new test, with no regression. Feature 11 changed a rule of feature 4 on purpose, and only the old assertion of that rule failed. P was the soonest on four of five features. Its time per feature grew by 32%, and D's by 32%, while A's moved 5%. That is the shape the hypothesis predicted for the plain tree, but D shows it too, and each arm has one tree. It is a direction to measure over a longer horizon, not a result.

Without the tool, the structure drifted as the code grew: D's tree went from 20 refusals of the generated import rules in 10 files to 24 in 12. A's tree cannot drift, since the tool refuses the violation.

E4. Real storage

Ports and adapters exist so that storage can change in one place. One fresh agent per tree moved everything to SQLite. A hidden test then restarted the server on the same file and read everything back.

All six trees passed, with no regression. The prediction on where the change lands held: no architecture run touched a context's domain or use cases, only adapters, wiring and the building blocks. The plain runs changed every module, since storage is not apart from the rules there. It did not make the change cheaper. P took 4.9 minutes, against 9.4–12.5 for A and 12.5–12.8 for D. Within the architecture arms, the size of the change followed a design choice, a table per aggregate or one document each, and not the arm.

What the four add to the first answer

On a small application, the architecture costs more under every condition where it was claimed to pay, and delivers no more. Two of its promises hold and are now measured: a change of storage stays out of the domain, and the structure does not drift when the tool holds it. Whether that return grows with the code is what OpenStay, a larger application built for longer, was then run to see.

What this still does not show

  • A longer horizon. Five more features on one tree per arm show a direction, not a result; OpenStay takes the same question past fifty features.
  • Another model family. The weaker model was the smallest of the same family.
  • Sample size. Two runs per arm in E1 and E4, one tree per arm in E3, two in E2.
