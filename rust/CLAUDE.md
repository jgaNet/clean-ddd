# Working on this repository (guide for AI assistance)

This is the **Rust implementation** of the Clean Architecture + Domain-Driven Design reference. The rules themselves, and what every language of the reference shares, are in the root [CLAUDE.md](../CLAUDE.md); this guide is Rust's: its commands, where its things are, how a feature is added here. Before changing anything, read the [README](README.md): it says what is written so far, how the decisions land in Rust, and maps every concept to the file that shows it. The TypeScript guide ([`typescript/CLAUDE.md`](../typescript/CLAUDE.md)) is the fuller one: the shape of a feature is the same, and the questions it answers (where a rule lives, whether an event needs a handler, which verb) are answered the same way here.

Every command below runs from this directory (`cd rust`).

## Commands

```bash
cargo run -p conventions                    # the crate graph is the table, the tree matches the binding, every named file exists, the inventory is current
cargo run -p conventions -- inventory       # the inventory read from this tree (docs/inventory/rust.json), in the words every language shares
cargo run -p conventions -- inventory --write   # writes it; the check refuses a committed inventory the tree no longer renders
cargo fmt --check                           # rustfmt (cargo fmt to apply)
cargo clippy --all-targets -- -D warnings   # the lints, warnings refused
cargo test                                  # every #[test], the end-to-end suites included; cargo test -p notes-domain for one crate, cargo test <name> for one test
cargo run -p bootstrap                      # serves the application on http://127.0.0.1:10000/v1
cargo run -p bootstrap-starter              # serves the composition a created application starts from: the Tracker alone
node ../api/scenario.mjs http://127.0.0.1:10000   # the API every language answers, against that server
yarn --cwd .. architecture rule <ID> | concept <id> | checklist <kind> | verb <intent>   # the contract, asked; from here it answers in Rust (`--language rust` says it explicitly)
                                            # the kinds: aggregate, value-object, domain-service, command, query, integration-event, event-handler, context
yarn --cwd .. architecture mode feature --base <ref>   # did this change leave the architecture alone (`--base working` for uncommitted changes; the default base is origin/main)
yarn --cwd .. conventions:write  # re-render README.md after editing conventions/rust.yaml
```

All four `cargo` checks must pass before a change is done; CI runs them on every PR, from this directory.

## Where things are

```
src/architecture/<layer>/         the building blocks, one crate per layer: domain (Entity, Aggregate, ValueObject, Id,
                                  Event, Exception, DomainResult), application (the handler traits, ExecutionContext,
                                  EventBus, Operation, Module), infrastructure (the in-memory adapters, ConsoleLogger),
                                  presentation (accept() and the refusals)
src/shared_kernel/<layer>/        domain (Email, Role), application (require_signed_in, integration_events/)
src/contexts/<context>/           one crate per layer (domain/, application/, infrastructure/, presentation/) and wiring/
                                  (notes, security, notifications, tracker)
  domain/src/<aggregate>/mod.rs   the aggregate; beside it <name>.rs value objects, events.rs, <aggregate>_exceptions.rs,
                                  dtos.rs (the snapshot), <rule>.rs domain services, ports/
  application/src/                commands/<use_case>.rs, queries/<use_case>.rs, events/<name>_handler.rs, the ports the
                                  Application owns (suggestions.rs)
  infrastructure/src/             the adapters, and the contract test of a port with several adapters
  presentation/src/               the routes of the context: a Router, a function per route, the bodies and the views
  wiring/src/lib.rs               local_<context>_module(): the Module as data, and what the context exports
src/bootstrap/                    the composition root (create_application.rs), the settings, the binary, and tests/:
                                  the end-to-end suites, over HTTP, with tests/support/mod.rs booting the application
  transport/                      crate bootstrap-transport: the transport, which names no context (axum_application.rs:
                                  the per-request identity and ExecutionContext, CORS, routes under the API prefix,
                                  listening; without an authentication layer every caller is anonymous)
  starter/                        crate bootstrap-starter: the composition root `create` gives a new application, the
                                  Tracker alone, with its entry point and its end-to-end suite (ADR 27)
tools/conventions/                the conventions check
../conventions/rust.yaml          this language's binding of the contract: contexts, trees, enforcers, checklists, canonical files
```

**Layers are crates.** A crate's `[dependencies]` are its row of the dependency table in [`conventions/architecture.yaml`](../conventions/architecture.yaml): `notes-domain` depends on `architecture-domain` and `shared-kernel-domain`, and on nothing else. Adding a dependency a row does not allow does not compile, and `cargo run -p conventions` names the rule. A crate is named after its tree and its layer (`architecture-domain`, `shared-kernel-domain`, `notes-domain`); its directory is the layer's name in lowercase. Inside a crate, a `use` names a sibling module (`super::note_title::NoteTitle`) or another crate by name; there is no path alias to bypass (ARCH-RELATIVE).

## The rules (enforced)

The rules are the contract's, the same in every language, and listed in the root [CLAUDE.md](../CLAUDE.md). What is Rust's is in [`conventions/rust.yaml`](../conventions/rust.yaml), this language's **binding**: the contexts, the trees, the libraries only an adapter may depend on, which tool holds each rule here (the crate graph for the dependency table, `cargo run -p conventions`, the compiler, a `#[test]`, review), what a new thing of each kind is made of (`yarn --cwd .. architecture checklist <kind>`), and the file that shows each concept and each rule.

- **The architecture is data.** A new context goes in `contexts` of the binding, with one crate per layer; a new file worth pointing at goes under `concepts` of the binding; a new rule goes in the contract, and in no binding. Neither is edited to make a violation pass.

## How to add a feature (follow an existing one, do not invent a shape)

Ask the contract first: `yarn --cwd .. architecture checklist <kind>` lists what a new one is made of in Rust and where it goes, with the placeholders filled in snake_case (typed from this directory it answers in Rust; `--language rust` says it explicitly). A plan is optional: `plan validate|explain` works on one that says `language: rust` ([`conventions/plans/share-a-note.rust.yaml`](../conventions/plans/share-a-note.rust.yaml) is the example), and is worth writing when a feature crosses a context or raises a modelling question. The questions the TypeScript guide answers under [*Questions you will have*](../typescript/CLAUDE.md#how-to-add-a-feature-follow-an-existing-one-do-not-invent-a-shape) — which verb, where a test goes, whether an event needs a handler, a guard on an event handler, what an archived thing refuses — are answered the same way here; read that list before guessing.

1. **Domain first.** Add a behaviour to the aggregate that enforces the rule and records an event ([`note/mod.rs`](src/contexts/notes/domain/src/note/mod.rs)): check the rules with `?` on the private `ensure_*` helpers, change the state, `self.root.record(NoteEvent::…)`, return `Ok(())`. A pure read skips the aggregate: its first step is a read model and a method on the queries port ([`note_queries.rs`](src/contexts/notes/domain/src/note/ports/note_queries.rs)). New concept with validation? A value object ([`note_title.rs`](src/contexts/notes/domain/src/note/note_title.rs)): a newtype, a private field, `create()` returning `DomainResult`, one exception per rule the user could act on differently in [`note_exceptions.rs`](src/contexts/notes/domain/src/note/note_exceptions.rs) (a `kind` constant and a constructor); a behaviour an archived note refuses reuses `ensure_active()` and its `NOTE_ARCHIVED`, since the remedy is the same (restore first). New rule about the whole collection, or a fact another context owns? A domain service generic over its port ([`note_sharing.rs`](src/contexts/notes/domain/src/note/note_sharing.rs)). A new fact is a new variant of the aggregate's event enum ([`events.rs`](src/contexts/notes/domain/src/note/events.rs)), named in the past tense, with its payload as fields. Tests at the bottom of the file.
2. **Command + handler**, in one file copied from [`edit_note.rs`](src/contexts/notes/application/src/commands/edit_note.rs): the command struct with its `NAME`, the handler generic over its ports with `execute()` — `require_signed_in` → load → ask the aggregate → `save(&note).await?` → `publish_domain_events(note, context).await`. Or a query handler from [`get_note.rs`](src/contexts/notes/application/src/queries/get_note.rs). One `pub mod` line in `commands/mod.rs` or `queries/mod.rs`; the tests of the handlers of one aggregate share the fixture at the bottom of [`commands/mod.rs`](src/contexts/notes/application/src/commands/mod.rs), with the in-memory repository as the double and the in-memory bus with a recording handler to see what was published — that recorder is subscribed per channel, so a new fact's name goes in the fixture's list of channels, or `published()` stays empty whatever the handler did.
3. **Infrastructure** only if a port changed. A new adapter of an existing port is added to `adapters()` in [`persistence_contract.rs`](src/contexts/notes/infrastructure/src/persistence_contract.rs) and must pass it unchanged; that is the whole review — the SQLite pair in [`repositories.rs`](src/contexts/notes/infrastructure/src/repositories.rs) and [`queries.rs`](src/contexts/notes/infrastructure/src/queries.rs) got in that way.
4. **Route + controller** in the context's `presentation` crate ([`notes/presentation`](src/contexts/notes/presentation/src/lib.rs)): one `async fn` per route, taking the request's `Extension<ExecutionContext>` and, for a query, the module from `State`. A command is `accept(&context, TheCommand { … })` — the `202` goes out, the dispatch runs after; a query is `module.query::<TheQuery>().handle(TheQuery { … }, &context).await`, answered through a view struct (`#[serde(rename_all = "camelCase")]`) or refused through the file's `refuse()`, which maps the context's own kinds before `status_of()`. A request body is a serde struct beside the route, and it says the body's shape and nothing else (API-BODY-SHAPE, [ADR 32](../docs/adr/0032-a-command-body-is-refused-for-its-shape-only.md)): its fields are `String`, `Vec<String>`, never an enum serde would refuse with a `422`, so that an unknown value reaches the domain, which refuses it on the operation (`Channel::parse_all()` and `UNKNOWN_CHANNEL`). An answer the HTMX front end also wants is a `const ByFormat` of two `Presenter`s, picked by `format_of(&headers)` ([`security/presentation/presenters.rs`](src/contexts/security/presentation/src/presenters.rs)); JSON is mandatory, HTMX optional. The verb follows the HTTP grammar (`yarn --cwd .. architecture verbs`): `POST /notes` creates, `PUT /notes/{id}` replaces, `POST /notes/{id}/share` acts; an action undone is a second `act` named after the undoing (`/archive` and `/restore`, `/pin` and `/unpin`), never a `DELETE`, which is for a thing that is truly gone. The HTMX front end is the presenters' example, not a second client to keep in parity: a new command does not oblige a new form control. Prove it end to end in [`src/bootstrap/tests`](src/bootstrap/tests): follow a `202` with `app.accepted(&client, response)`, which polls the operation to its outcome. The end-to-end suite and the shared scenario ([`api/scenario.mjs`](../api/scenario.mjs)) assert the exact shape of every response, field count included: a feature that changes what a client sees (a new field, a new route) fails the scenario against this server until the other languages carry it, which is the point of [ADR 16](../docs/adr/0016-one-api-for-every-language.md); the feature is done in its language when its end-to-end suite proves it, and the scenario is then the list of what the other languages owe.
5. **List it in the wiring** ([`wiring/src/lib.rs`](src/contexts/notes/wiring/src/lib.rs)): `Subscription::command(handler)` for a command, `query(handler)` for a query, `Subscription::reaction("<TheFact>", handler)` for a reaction.
6. Cross-context reaction? Publish an integration event from a domain event handler with `publish_integration_event(event, context).await` ([`notes/.../note_shared_handler.rs`](src/contexts/notes/application/src/events/note_shared_handler.rs)): the contract is an enum in the shared kernel's `integration_events/`, with its published name. The consuming context reacts with an anti-corruption handler in its own `events/` ([`notifications/.../note_shared_handler.rs`](src/contexts/notifications/application/src/events/note_shared_handler.rs)): it knows the contract and nothing else of the other context, restates the fact in its own words, and calls its own use case; listed in its wiring under `integration_events`, on the contract's published name.
7. **The map.** A new file worth pointing at goes under `concepts` in [`conventions/rust.yaml`](../conventions/rust.yaml); then `yarn --cwd .. conventions:write` and `cargo run -p conventions`. A second use of a kind the map already shows (another command on an aggregate, another route) is not a new example: the map stays as it is, and a feature does not edit the binding.

## Questions you will have, in Rust words

The TypeScript list linked above is the full one; these are the answers a Rust reader reaches for most, in this language's vocabulary.

- **Where do my events go after `publish_domain_events()`?** Into the unit of work's outbox at commit (a `before_commit` step), then through the bus once the commit is through, each under its entry's id ([ADR 24](../docs/adr/0024-events-are-durable-before-they-are-published.md)); a rollback drops them, a relay that fails leaves them pending for the next one, and the bus hands a message to a subscriber once, by its id. A reaction is no different: the provided `handle()` runs it in a transaction of its own (ADR 30). Nothing of this is the handler's to write.
- **A reaction that saves, publishes, or tells several people?** The provided `handle()` of [`EventHandler`](src/architecture/application/src/event_handler.rs) runs `execute()` in a transaction of its own, in a context of its own (`context.for_reaction()`, a unit of work from `UnitOfWork::another()`; [ADR 30](../docs/adr/0030-a-reaction-is-a-transaction-of-its-own.md)): save what it changes, call `publish_domain_events()` for an aggregate it changed and `publish_integration_event()` for a fact it tells other contexts ([`note_shared_handler.rs`](src/contexts/notes/application/src/events/note_shared_handler.rs)) — never `context.publish()`, which goes straight to the bus — and return an `Err` (`?` on the first refusal) to undo all of it. A fan-out (one notification per recipient) that fails half-way is undone whole, so a second delivery starts clean: do not make a reaction idempotent by hand. The facts a reaction needs are the ones of that moment, so the domain event carries them (who the note was shared with when it was archived) rather than the reaction reading them back; a time in an integration event's payload is an ISO 8601 `String`, since the contract crosses a boundary (inside a context, a domain event may carry a typed time). A context that only consumes cannot show its reaction in its own end-to-end suite (a suite under `src/bootstrap/tests/` speaks HTTP and may not reach the bus): the handler's `mod tests` shows it, and the flow is shown end to end where both contexts are wired.
- **Does every domain event need a handler?** No. The aggregate records the fact because it happened (`NoteEvent::Edited` has no handler); subscribe one in the wiring only when something reacts. An integration event exists only once a first consumer needs the fact.
- **An existing event needs more data for a new consumer?** Widen the variant in `events.rs` and the `record()` call in the behaviour, which holds the state; do not add a second variant for the same fact. One fact is one message: a fact with several interested parties is one event carrying the list (`shared_with`), and the fan-out is the consumer's business. The contract names it in Notes' public words (`recipient_ids`), and is published whenever the fact happens, the list empty or not.
- **A second fact in a contract enum?** It is a second variant of the enum in `integration_events/` (the contract is one enum per publishing context, ADR 12). Every existing consumer of that enum then has a refutable pattern: its `let NoteIntegrationEvent::Shared { .. } = event;` becomes `let … = event else { return Ok(()) };`, as [`account_validated_handler.rs`](src/contexts/notifications/application/src/events/account_validated_handler.rs) already reads. Editing the canonical consumer for that one line is expected, not a smell.
- **Do event handlers need a guard?** No. A domain or integration event handler reacts to a fact that was already allowed, with the publisher's caller (in a context and a transaction of its own, ADR 30); the `EventHandler` trait has no `guard()`. An anti-corruption handler that fans out calls the local use case once per recipient, passes the first `Err` on with `?`, and answers `Ok(())`.
- **Does the read side's order matter?** Yes, and it belongs to the queries port: the order a method returns is in its doc comment ([`note_queries.rs`](src/contexts/notes/domain/src/note/ports/note_queries.rs)) and asserted for every adapter by the contract test. A query handler never sorts; an adapter does (a stable `sort_by_key` in memory, an `ORDER BY` in SQL).
- **Does a new kind need a line in `refuse()`?** No. It maps *kinds* (`NOT_ALLOWED` → 403, the aggregate's not-found kind → 404, anything else → 400); a refused command never reaches it, it is on the operation.
- **Which HTTP verb?** `yarn --cwd .. architecture verb <intent>`: `GET` for a query, `POST` to create and for an action on a thing, `PUT` to replace, `PATCH` for a partial state change, `DELETE` for a thing truly gone. A toggle is two acts (`/pin` and `/unpin`), never a `DELETE`.
- **Where does the test go?** Beside what it tests, in a `#[cfg(test)] mod tests` at the bottom of the file: the aggregate's in `note/mod.rs`, the handlers of one aggregate in the fixture of `commands/mod.rs` (a new fact's name goes in its list of channels), one case per adapter in the contract test, each event handler's in its own file, the user-visible flow in `src/bootstrap/tests/`. A rule in a `guard()` override is tested through `handle()`.
- **How do I compare things in a test?** An event, a snapshot and a read model derive `PartialEq`: `assert_eq!` compares every field, so a recorded event is asserted with its whole payload. An aggregate keeps its state private: compare with `equals()` or through `to_snapshot()`. A `DomainResult` is matched: `Err(exception)` and `exception.kind()`.
- **Module declarations?** A new file is one `pub mod` line in its directory's `mod.rs`; the `commands/`, `queries/` and `events/` directories also `pub use` what the wiring lists, so a wiring file names `notes_application::events::NoteArchivedHandler` and not the module path. No re-export of a port's adapter, and no barrel in `ports/`.

## Code style

- Edition 2024, `cargo clippy --all-targets -- -D warnings` clean, `cargo fmt` applied (`rustfmt.toml`: 120 columns).
- Private fields everywhere in the domain; the only way into an aggregate is `create()` or `from_snapshot()`, the only way into a value object is `create()`. Accessors return references or copies, never `&mut`.
- `DomainResult<T>` in every signature that can refuse; `?` to pass a refusal on; `panic!` only for corrupted state, with the id in the message. No `unwrap()` outside tests; `expect("why")` in tests. A handler never catches: the provided `handle()` is the safety net.
- A handler takes its ports in `new()`, generic over their traits, shared in `Arc` with the other handlers of the aggregate; the only state it holds is those ports (ARCH-EXECUTION-CONTEXT: a clock, a mailer, a model client is such a port, never a member of the context).
- Only [`logging.rs`](src/architecture/infrastructure/src/logging.rs) and the tools print: the workspace denies `println!` and `eprintln!` everywhere else; a handler logs through `context.logger()`.
- `snake_case` files named after what they hold (`note_title.rs`, `note_sharing.rs`); `PascalCase` types; a `kind` constant in `SCREAMING_CASE` per rule (`NOT_NOTE_OWNER`); enum names in the outside world are the variant in uppercase (`NoteStatus::Active.as_str() == "ACTIVE"`).
- A doc comment (`//!` at the top of a file, `///` on an item) explains *why* the file exists and what rule it protects, in a few lines. No commented-out code.
- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`), one concern per PR, and the PR body states how it was verified.

## Things to avoid

- A trait object or a generic base type that reintroduces inheritance (`Box<dyn Aggregate>`); the aggregate holds its `AggregateRoot` and that is the whole mechanism.
- A dependency a crate's row does not allow, however convenient: the compiler says no, `cargo run -p conventions` says which rule, and the fix is a port, an integration event or a move — never an edit to the binding.
- A rule in `conventions/rust.yaml`: a binding points at files and holds no rule (ARCH-ONE-CONTRACT).
- A `Result` type of our own, a `Mapper`, a generic `Repository<T>`, a service locator or a DI container.
- A runtime dependency (`tokio`) below the Presentation layer — it is a listed library, and the check refuses it there: the ports are `async` by shape, the tests drive them with `pollster`, the bus awaits the handlers inline, and `accept()` in the Presentation building block is where the dispatch is spawned.
- Overriding `handle()` or `run()`: they are the template method, the same for every handler; what differs goes in `execute()` or `guard()`.
- Naming a handler's concrete type from a controller (`module.query::<GetNoteQueryHandler<InMemoryNoteQueries>>()`): it would name the adapter, which the Presentation may not see. Ask by the message: `module.query::<GetNote>()`, `module.command::<Login>()`.
- Publishing a command whose answer must not be recorded (a login's token) — run it through the module instead, and let the Tracker see nothing.
